# Semantic Topic Identity v0 — Canonical Schema Contract (S1 + S2A)

Status: **S1 (schema-only, fully inert) + S2A (writerless audit/provenance schema + temporal hardening) implemented locally.** S1: `supabase/migrations/072_semantic_topic_identity_foundation.sql`. S2A: `supabase/migrations/073_semantic_topic_s2a_audit_and_temporal_hardening.sql`. Neither phase has an RPC, a trigger, a backfill, a cron, a route, a UI, a TypeScript caller, an AI/provider call, or any data write — S2A adds three new tables and hardens the temporal invariant on the S1 membership table, but nothing in either phase can create a single row of application data by itself (`service_role` is `SELECT`-only on every table this contract covers).

## 1. Source of truth and precedence

This contract reflects the single, final specification for this phase: **"PFM Semantic Topic Identity v0 — Final SQL Correctness Correction Gate."** It was preceded by two earlier, now-superseded design passes (a conceptual layer model, then a first exact-schema draft) recorded only in prior session memory — those are historical context, not a separate source of truth; wherever this document and that history would differ, this document and migration 072 win.

The decision to build this at all follows directly from a calibration-audit finding recorded against the existing Shadow Topic v0 pipeline (see `docs/architecture/shadow-topic-v0-contract.md`, and below, §9): the current single production `signal_clusters` row is semantically incoherent — it mixes ten unrelated stories under one `(category, seed_text)` fingerprint, because the scheduled-discovery capture path that populates it does no similarity check at all. Semantic Topic Identity is the planned replacement layer; S1 is only its schema foundation.

## 2. Scope — exactly two tables, nothing else

`semantic_topics` and `semantic_topic_membership`. No event table, no decision table, no lineage table, no scoring table, no lane table, no Creative DNA table. No RPC, no trigger, no backfill, no data write, no `ALTER` on any pre-existing table — not `signal_clusters`, not `signal_cluster_evidence`, not `signal_score_runs`/`signal_cluster_scores`, not `signal_evidence`, not the 070/071 scoring function, not the collector/control/seed tables, not `creator_memory`/`video_ideas`.

Explicitly **not** in S1 (deferred to a later phase, together with their writer RPCs): `semantic_topic_membership_events`, `topic_assignment_decisions`, `semantic_topic_lineage_operations` + `edges`. These arrive, if at all, only alongside the SECURITY DEFINER writer RPC that would populate them — following the same "empty validated schema first, writer later" pattern the Shadow Topic v0 069→070 migrations used.

## 3. Legacy discovery bucket vs. semantic topic — two different concepts, deliberately kept apart

`signal_clusters` (the existing legacy table) is a **discovery bucket**: a deterministic text-fingerprint grouping keyed on `(category, seed_text)`, produced by the scheduled-discovery capture path with no semantic similarity check. It is what the Shadow Topic v0 scoring pipeline (069–071) currently scores, and it is known to be semantically incoherent in production today.

`semantic_topics` is a **semantic identity**: a candidate real-world topic, asserted by a specific evidence-linking event and tracked through an explicit lifecycle (`candidate_singleton` → ... → `coherent`/`split_required`/`merge_candidate`/`superseded`/`archived`). The two concepts are intentionally not merged into one table and not cross-referenced by any FK in S1 — `semantic_topics` does not point at `signal_clusters`, and nothing in S1 alters how `signal_clusters` is populated or scored. The legacy discovery-bucket pipeline (collector, `signal_clusters`, Shadow Topic v0 scoring) continues to run completely unchanged after this migration.

## 4. `semantic_topics`

One row per candidate semantic topic identity.

| Column | Type | Notes |
|---|---|---|
| `id` | `UUID PK` | `gen_random_uuid()` |
| `lifecycle_status` | `TEXT NOT NULL DEFAULT 'candidate_singleton'` | `candidate_singleton` \| `corroborating` \| `coherent` \| `ambiguous` \| `split_required` \| `merge_candidate` \| `superseded` \| `archived` |
| `canonical_label` | `TEXT NOT NULL` | non-blank after `btrim` |
| `label_language` | `TEXT NOT NULL` | see §6 |
| `specificity` | `TEXT NOT NULL DEFAULT 'unknown'` | `specific` \| `generic` \| `unknown` |
| `creation_request_digest` | `TEXT NOT NULL` | 64 lowercase hex chars, `UNIQUE` — see §5 |
| `status_version` | `INTEGER NOT NULL DEFAULT 1` | `>= 1` |
| `created_at` | `TIMESTAMPTZ NOT NULL DEFAULT now()` | |
| `updated_at` | `TIMESTAMPTZ NOT NULL DEFAULT now()` | see §7 |

Deliberately absent: a `UNIQUE` constraint on `canonical_label` (two topics may legitimately share a label — disambiguation is a semantic, not a textual, problem), a self-referencing `superseded_by_topic_id`/`split_from_topic_id` column (a normalized `operation_id` + `edges` model is the planned S2/S3 shape, not a half-built self-FK), any writer trigger, any lifecycle RPC, and any automatic `updated_at`-touching trigger.

## 5. `creation_request_digest` — request-idempotency only, not semantic identity

This field exists solely so that a retried creation request (same caller, same inputs, same call) does not create a duplicate row. It is **not** a semantic deduplication key: two different evidence items describing the same real-world phenomenon, submitted as two different creation requests, will legitimately produce two different `semantic_topics` rows with two different digests. Reconciling those two rows into one is a cross-evidence semantic problem — **DEFERRED_TO_S2** (embedding-similarity retrieval and/or manual-review adjudication, resolved through the `merge_candidate` lifecycle state, audited by whatever event/decision table S2 introduces). S1 has no writer, so no digest, duplicate or otherwise, can exist yet outside a test fixture.

## 6. `label_language` — v0-supported canonical BCP-47 subset

`CHECK (label_language ~ '^[a-z]{2,3}(-[A-Z][a-z]{3})?(-[A-Z]{2})?$')` plus `CHECK (length(label_language) <= 15)`.

This is **a deliberately narrow, v0-supported subset of BCP-47** — not a general BCP-47 validator. It accepts: a 2–3 lowercase-letter primary subtag alone (`en`, `hu`, `id`, `und`); a primary subtag plus a 4-letter Titlecase script subtag (`zh-Hans`); a primary subtag plus a 2-letter uppercase region subtag (`pt-BR`); or all three combined (`zh-Hant-TW`). It rejects an empty string, an all-uppercase primary subtag (`ENG`), an underscore-separated locale (`hu_HU`), and a lowercase region subtag (`pt-br`) — case and separator matter, exactly as in real BCP-47, but subtag combinations and extensions (variants, extensions, private-use tags) beyond this fixed shape are out of scope and will be rejected even if they are valid BCP-47 in the abstract. Widening this regex, if a future language ever needs a shape outside it, is a schema change, not a runtime concern.

## 7. `updated_at` / `status_version` — S1 declares the field, S2 owns the behavior

Both columns exist in the S1 schema so that a future writer does not require a schema migration to start using them, but **S1 itself never writes a second row and never updates a first one** (there is no writer at all — see §10). The transactional semantics — that `status_version` increments exactly once per accepted lifecycle transition, and `updated_at` moves in the same transaction as any content or lifecycle change — are a S2 SECURITY DEFINER writer RPC's responsibility, not a DB trigger. No trigger enforces this in S1, and none should be inferred from the column's presence.

## 8. `semantic_topic_membership`

One row per (evidence, topic) assignment interval — the temporal join between evidence and semantic identity.

| Column | Type | Notes |
|---|---|---|
| `id` | `UUID PK` | |
| `semantic_topic_id` | `UUID NOT NULL FK → semantic_topics(id) ON DELETE RESTRICT` | |
| `signal_evidence_id` | `UUID NOT NULL FK → signal_evidence(id) ON DELETE RESTRICT` | |
| `valid_from` | `TIMESTAMPTZ NOT NULL DEFAULT now()` | |
| `valid_to` | `TIMESTAMPTZ NULL` | `NULL` = currently active; `CHECK` requires `valid_to > valid_from` when set |
| `assignment_reason` | `TEXT NOT NULL` | `entity_event_match` \| `embedding_similarity` \| `manual_review_confirmed` \| `manual_review_override` |
| `confidence` | `NUMERIC(5,4) NOT NULL` | `0 <= confidence <= 1`, both endpoints allowed |
| `algorithm_version` | `INTEGER NOT NULL` | `>= 1` |
| `created_at` | `TIMESTAMPTZ NOT NULL DEFAULT now()` | |

This is the **canonical membership source of truth** — an evidence item's current semantic topic is "the row with `valid_to IS NULL`," and its full assignment history is every row for that `signal_evidence_id` ordered by `valid_from`. There is no separate `_events` audit table in S1; the membership table itself is the history, via closed (`valid_to`-set) rows.

### Indexes

- `semantic_topic_membership_active_evidence_key` — `UNIQUE (signal_evidence_id) WHERE valid_to IS NULL`. Enforces **at most one active membership per evidence item**.
- `idx_semantic_topic_membership_active_topic` — `(semantic_topic_id) WHERE valid_to IS NULL`. Fast "current members of this topic" lookups.
- `idx_semantic_topic_membership_temporal` — `(semantic_topic_id, valid_from, valid_to)`. Fast historical/point-in-time queries.

### Temporal non-overlap — DEFERRED_TO_S2

The partial unique index above guarantees only that an evidence item has **at most one currently-active** membership. It does **not** guarantee that an evidence item's full history of *closed* intervals never overlaps in time (e.g. two rows both claiming `valid_from=T1, valid_to=T3` and `valid_from=T2, valid_to=T4` with `T1<T2<T3<T4`). A true non-overlap guarantee would need `EXCLUDE USING gist (signal_evidence_id WITH =, tstzrange(valid_from, valid_to) WITH &&)`, which requires the `btree_gist` extension. **That extension is not installed by this migration and not assumed to be installed anywhere.** `TEMPORAL_NON_OVERLAP = DEFERRED_TO_S2`.

Because S1 has no writer (see §10), this is a structurally inert gap today — no code path can insert a membership row, let alone an overlapping one. Before any S2 writer RPC is allowed to write to this table, it must either (a) perform an application-level overlap check inside the same transaction, serialized behind a `pg_advisory_xact_lock` keyed on the evidence id, or (b) a separately approved migration must add the `btree_gist` exclusion constraint. One of those two is a hard prerequisite for the S2 writer, not an optional hardening step.

## 9. Lifecycle — states declared, runtime transitions DEFERRED_TO_S2

The eight `lifecycle_status` values are declared and `CHECK`-enforced as a closed set, but **no code enforces which transitions between them are legal** (e.g. that `archived` cannot go back to `candidate_singleton`). S1 is schema-only: any value in the enum can be written to any row at any time by a direct (test-only, since `service_role` has no `INSERT`/`UPDATE`) write. State-machine enforcement is a S2 writer-RPC responsibility. `LIFECYCLE_RUNTIME_ENFORCEMENT = DEFERRED_TO_S2`.

## 10. No writer in S1 — structurally, not just by convention

Both tables grant `service_role` **`SELECT` only**. `anon`/`authenticated`/`PUBLIC` have zero privileges on either table. There is no sequence, no function, no trigger associated with either table. This means: **no application code path, however buggy, can write a row to either table today** — not through the app's normal Supabase client (which authenticates as `service_role` or an end-user JWT, never as `postgres`), and not through any existing RPC (069–071's `run_shadow_topic_scoring` never references these tables). The only way a row can exist in either table right now is a manual `postgres`-privileged `INSERT`, which is exactly what the test fixtures in §12 do and nothing else does.

## 12. Fail-closed migration contract

072 follows the same fail-closed idempotency pattern as 069 (Shadow Topic v0 schema): a `DO` block per table checks existence first. If the table is absent, it runs the `CREATE` branch (table + indexes + RLS + grant). If the table is already present, it runs a `VALIDATE` branch that never executes DDL/DCL — it only compares the live column/constraint/index/RLS/policy/grant state against the exact expected shape, and `RAISE EXCEPTION`s on any mismatch (drift), with no auto-repair and no `DROP`/`RECREATE`.

072 adds one more layer ahead of both per-table blocks: a **global topology gate**. It counts how many of the two target tables currently exist. `0` means both blocks will take the `CREATE` branch; `2` means both will take the `VALIDATE` branch; `1` (a partially-applied prior attempt) triggers an immediate `RAISE EXCEPTION` before either per-table block runs, so a half-applied state can never proceed into a `CREATE` on the missing table. Verified locally: running 072 twice against a clean DB is a byte-exact no-op on the second run (confirmed via the DB-integration re-run test, §13), and forcing a 1-of-2 state (dropping one table only) causes the gate to raise before any DDL executes, leaving the surviving table completely untouched (the whole migration is one `BEGIN`/`COMMIT` transaction).

`tests/semantic-topic-identity-schema-db-integration.test.ts` — same pattern as the existing `shadow-topic-score-schema-db-integration.test.ts`: runs only against the existing local Docker Supabase stack (`supabase_db_WillViralFinal`), skips entirely (not a failure) when that stack is unavailable, uses direct `postgres`-privileged `psql` fixture inserts (there being no writer RPC to call instead), and uses `SET ROLE` for real grant-boundary checks. It explicitly does **not** claim to test temporal non-overlap across closed intervals — per §8, that guarantee does not exist in S1, and the test suite documents this rather than asserting a false pass.

# S2A — Writerless Audit/Provenance Schema + Temporal Hardening

S2A adds three new, still-writerless tables and closes the S1 `TEMPORAL_NON_OVERLAP = DEFERRED_TO_S2` gap. It does **not** add a writer RPC — that is S2B/S2C. Canonical source: "PFM Semantic Topic Identity v0 — S2 Final Pre-Implementation Correctness Gate."

## 15. `topic_extraction_runs` — one row per terminal extraction attempt

**Terminal, immutable model (not start/finish):** `status` is `CHECK (status IN ('completed', 'failed'))` — there is no `processing` value in the schema. The table records only settled attempts; a crash/timeout that never reaches a settlement is tracked by the provider-reservation system (059–066), not here. There is **no** `invalidated_at` or `superseded_by_extraction_run_id` — the table is genuinely INSERT-only, never UPDATE, so calling it immutable is not just a claim no code path contradicts.

**Two-layer provenance**, replacing the earlier single "input_snapshot" idea:
- `source_snapshot` / `source_snapshot_digest` — built **by a future RPC directly from the live `signal_evidence` row**, never accepted as client JSON. Digest computed server-side.
- `normalized_extraction_input` / `normalized_input_digest` — the actual normalized text the extractor consumed; caller-supplied (normalization happens in the application layer), but the digest is recomputed server-side from the supplied text, so it is at least self-consistent (though it cannot prove the normalization *process* was correct).

**Provider/model/prompt pairing** — explicit two-branch, fully-closed CHECK: `deterministic` requires `provider`/`model`/`prompt_version` all `NULL` and `deterministic_extractor_version` set; `ai_assisted` requires all three non-blank (length-bounded) and `deterministic_extractor_version NULL`. No partial combination on either branch is legal.

**Cache identity** — `extraction_config_digest` (hash of `extraction_method, normalization_version, extraction_schema_version, provider, model, prompt_version, deterministic_extractor_version`) plus `(signal_evidence_id, normalized_input_digest)` forms the cache key. A **partial unique index** (`topic_extraction_runs_completed_cache_key`, `WHERE status = 'completed'`) allows at most one completed result per exact cache key, while `failed` attempts may retry indefinitely under fresh `idempotency_key`s. `idempotency_key` remains pure request-idempotency, unrelated to cache identity.

**`structured_output`** (only present when `status='completed'`) must conform to the `topic_extraction_output_v1` contract — enforced by CHECK as far as a non-subquery expression allows: object type, **no unknown top-level keys** (`structured_output - ARRAY[...] = '{}'`), required scalar fields present/typed/length-bounded, `label_language` against the same S1 BCP-47 subset regex, `specificity`/`content_format` enums, `confidence` range, `subject_entities`/`supporting_spans` array-typed with bounded length, and the embedded `extraction_schema_version` cross-checked against the column. Per-element structure inside the arrays (e.g. each `supporting_spans` object's own shape) is **not** DB-enforceable via CHECK (Postgres CHECK constraints cannot contain subqueries or set-returning functions) — that remains an S2B/RPC responsibility. `supporting_spans` elements are `{source_field, quoted_text}` only — **no offsets** (avoids UTF-16/codepoint/Postgres-index ambiguity); `quoted_text` is expected, not DB-enforced, to be a verbatim substring of the corresponding `source_snapshot` field.

`estimated_cost_usd`/`input_tokens`/`output_tokens` are **diagnostic only**, not wired to the collector's `signal_provider_daily_budgets`/`reserve_provider_units` system in any way in S2A (see §18).

## 16. `topic_assignment_decisions` — one row per settled assignment decision

`UNIQUE(extraction_run_id)` — exactly one decision per extraction, 1:1. `outcome IN ('CREATE_NEW', 'ATTACH_EXISTING', 'QUARANTINE')`, paired with `semantic_topic_id`/`resulting_membership_id` (both NULL iff `QUARANTINE`, both NOT NULL otherwise). `decision_reason` is a 7-value enum; S2's own (not-yet-written) RPC will in practice only ever produce `no_similar_topic_found` and `exact_entity_match` — `embedding_similarity_match` and the `manual_review_*` values are schema-reserved for S3. No `invalidated_at` — same immutability stance as `topic_extraction_runs`.

## 17. `semantic_topic_membership_events` — append-only decision-provenance log

Complements (does not duplicate) the S1 membership table's own temporal history: the membership table records *what was true when*, this table records *why a transition happened and under which decision*. `related_assignment_decision_id` is **`NOT NULL`** — every event, including any future manual correction, must carry a real `topic_assignment_decisions` row; there is no audit-free nullable escape hatch. `event_type IN ('attached', 'detached', 'reassigned')`.

## 18. `semantic_topic_membership.assignment_reason` — `topic_creation_seed` added

The original 072 four-value enum (`entity_event_match`, `embedding_similarity`, `manual_review_confirmed`, `manual_review_override`) had no value that correctly describes a `CREATE_NEW` topic's first membership — it isn't a *match* to anything pre-existing. S2A adds a fifth value, **`topic_creation_seed`**, via a fail-closed `DROP CONSTRAINT`/`ADD CONSTRAINT` pair that only proceeds from the exact, byte-verified 072 legacy definition (or is a no-op if already corrected) — any other observed definition is `DEFINITION_DRIFT`, migration aborts, no auto-repair.

## 19. Temporal non-overlap — `DEFERRED_TO_S2` closed

### `btree_gist` install — fail-closed preflight, not just post-install validation

Before any DDL runs, the `NOT EXISTS` branch checks **two facts from the live catalog**: `pg_available_extension_versions` genuinely offers the expected version (`1.7`) on this PostgreSQL installation, and the target schema (`extensions` — the same convention `pgcrypto` already uses) exists. ("No `btree_gist` already installed in a different schema" is not a separate query — `pg_extension` can hold at most one row per extension name per database, so reaching this branch at all already proves that fact.) Either preflight failure is `RAISE EXCEPTION` before `CREATE EXTENSION` is ever issued. An already-present extension is checked for exact `(extversion, extnamespace)` match and left untouched otherwise (`RAISE EXCEPTION` on mismatch, never `ALTER`/`DROP EXTENSION`).

**The `VERSION` clause and its `WARNING` — documented precisely, not just described.** Command actually run when the extension is absent:

```sql
CREATE EXTENSION btree_gist WITH SCHEMA extensions;
```

An earlier draft of this migration also appended `VERSION '1.7'`. Running that variant (`CREATE EXTENSION btree_gist WITH SCHEMA extensions VERSION '1.7';`) as the `postgres` role — confirmed non-superuser on both local (`supabase_admin` holds superuser locally) and production — produces, verbatim, from the **PostgreSQL server's own `CREATE EXTENSION` DDL processing** (not psql, not the extension's install script):

```
WARNING:  only superusers can specify extension versions, ignoring version "1.7" and installing the default version
```

The clause is silently dropped and the default version installs instead — which happens to equal `1.7` here only because it is the *only* version `pg_available_extension_versions` currently offers for `btree_gist` on this PostgreSQL build, not because the clause took effect. The migration therefore does not pass `VERSION` at all (it would be theater), and instead makes the guarantee real via a **post-install self-check in the same transaction** — `extversion`/`extnamespace` are re-read immediately after `CREATE EXTENSION` and compared against the expected values; any mismatch `RAISE EXCEPTION`s. Verified locally by forcing both failure modes: an unavailable-version preflight failure leaves `pg_extension` with **zero** `btree_gist` rows (never reached `CREATE EXTENSION`), and a forced post-install self-check failure (extension genuinely installs as `1.7`, self-check deliberately told to expect something else) *also* leaves zero rows afterward — proving the single-transaction rollback undoes the extension creation itself, not just the error propagation.

### The `EXCLUDE` constraint — a real unbounded range, not an `infinity` sentinel

```sql
ALTER TABLE semantic_topic_membership ADD CONSTRAINT semantic_topic_membership_no_overlap
  EXCLUDE USING gist (
    signal_evidence_id WITH =,
    tstzrange(valid_from, valid_to, '[)') WITH &&
  );
```

An earlier draft used `tstzrange(valid_from, coalesce(valid_to, 'infinity'::timestamptz), '[)')`. That is a real, storable `timestamptz` value standing in for "no upper bound" — not PostgreSQL's native unbounded-range representation, and nothing stopped a caller from writing the literal `'infinity'` timestamp into `valid_to` directly. The corrected form passes `valid_to` straight through: PostgreSQL's range constructor treats a `NULL` bound as genuinely unbounded (`upper_inf(...)` returns true, confirmed locally), which participates correctly in `&&` overlap comparisons without a sentinel value anywhere.

That alone doesn't stop `'infinity'`/`'-infinity'` from being written as an *explicit* value, so two more `CHECK` constraints close that gap directly, added via the same fail-closed CREATE/VALIDATE pattern (with a real precheck over existing rows before either is added):

- `semantic_topic_membership_valid_from_finite` — `CHECK (isfinite(valid_from))`
- `semantic_topic_membership_valid_to_finite` — `CHECK (valid_to IS NULL OR isfinite(valid_to))`

Verified locally: `valid_from`/`valid_to` = `infinity` or `-infinity` are all rejected (the `-infinity` `valid_to` case is caught by the pre-existing 072 `valid_to > valid_from` CHECK before it would even reach the new guard — both agree the row is invalid). An **empty range** can never be constructed either way: the only way a `tstzrange` becomes empty is a lower bound `>=` the upper bound, which the 072 `valid_to > valid_from` CHECK already excludes independently of the range-type machinery.

A mandatory **overlap precheck** (a real self-join over the live table, using the same finite `tstzrange` expression as the constraint itself) runs immediately before `ADD CONSTRAINT` and `RAISE EXCEPTION`s if any pre-existing overlapping pair is found — the constraint is never added over already-invalid data. Half-open `[valid_from, valid_to)` semantics mean **touching, non-overlapping intervals are explicitly allowed** (`[a,b)` followed by `[b,c)`). Verified locally: active–active, active–historical, and historical–historical overlaps for the same `signal_evidence_id` are all rejected; two genuinely concurrent overlapping inserts resolve to exactly one success. This constraint is defense-in-depth alongside (not a replacement for) whatever advisory-lock discipline a future S2B writer RPC also implements.

`TEMPORAL_NON_OVERLAP` is no longer `DEFERRED_TO_S2` as of this migration — it is closed at the schema level, for every current and future write path, including ones that don't yet exist.

## 20. Phase boundaries (S2A / S2B / S2C / S3)

- **S2A** (this migration): the three audit tables, the `assignment_reason` enum correction, `btree_gist` + the `EXCLUDE` constraint. Zero RPCs, zero provider/quota changes.
- **S2B** (not started): the two writer RPCs (`record_topic_extraction_run`, `record_topic_assignment_decision`) implemented and tested locally against **synthetic, deterministic-only** payloads. No production, no provider.
- **S2C** (not started): the S2B RPCs applied to production, inert — no application caller exists yet.
- **S3** (not started): the AI-provider/quota contract (a real architectural change to the existing `reserve_provider_units` RPC and its `usage_type`/`provider` CHECK constraints — confirmed by code audit to be non-trivial, not a simple additive row), an application-layer extraction service, and a controlled, explicitly-approved shadow replay over the 10 existing production evidence rows.

# S2B — Writer RPCs

S2B implements the two writer RPCs S2A left as still-unwritten (§20): `public.record_topic_extraction_run(...)` and `public.record_topic_assignment_decision(...)`. Both are `SECURITY DEFINER`, local-only (no production application caller exists yet — that arrives, inert, in S2C). Canonical source for the two design decisions below: **"PFM Semantic Topic Identity v0 — S2B Local Design Closure"** (chat-delivered, explicit, separate from the S2 Final Pre-Implementation Correctness Gate that closed §15–19 — those left the confidence threshold and lifecycle-transition rule genuinely undefined, and implementation correctly stopped with `DESIGN_CONTRACT_INCOMPLETE` until this closure supplied them).

## 23. Design-closure constants — pinned, not invented

**`v_min_confidence = 0.8500`** (`NUMERIC(5,4)`). Gates `CREATE_NEW` and `ATTACH_EXISTING` in `record_topic_assignment_decision`: `structured_output.confidence` must be `>= 0.8500` or the RPC `RAISE EXCEPTION`s — never silently downgrades to `QUARANTINE`; that decision belongs to the calling application, which must retry with `outcome='QUARANTINE'` and `decision_reason='below_confidence_threshold'` instead. **Not** enforced on `QUARANTINE` itself — an app already choosing to quarantine may do so for any confidence/specificity. Boundary-tested: `0.8500` accepted, `0.849999` rejected. The comparison is deliberately done through a plain `NUMERIC` PL/pgSQL variable, not a `NUMERIC(5,4)`-typed one — assigning `0.849999` to a `NUMERIC(5,4)` variable rounds it *up* to `0.8500` before any comparison runs, which would silently accept a value the contract requires rejected. Only the later `INSERT`s into the real `NUMERIC(5,4)` columns (`semantic_topic_membership.confidence`, `topic_assignment_decisions.model_confidence`) round it, strictly after the threshold check already ran correctly. `CREATE_NEW`/`ATTACH_EXISTING` also require `structured_output.specificity = 'specific'` — `generic`/`unknown` are always rejected, independent of confidence.

**Lifecycle transition — exactly one automatic rule, everything else deferred.** `CREATE_NEW` sets no lifecycle fields explicitly; the new topic gets the `semantic_topics` column defaults (`lifecycle_status='candidate_singleton'`, `status_version=1`). `ATTACH_EXISTING` performs **at most one** automatic transition: if the target topic's lifecycle_status is (still) `candidate_singleton` and the just-inserted membership brings its **active membership count to `>= 2`**, the RPC sets `lifecycle_status='corroborating'`, `status_version = status_version + 1`, `updated_at = now()` — in the same transaction as the membership insert. Every other combination is a deliberate no-op: `corroborating` stays `corroborating` (no automatic `corroborating→coherent` rule exists in S2B — that's a later phase), `coherent` stays `coherent`, `ambiguous` stays `ambiguous` (subject to the ATTACH-matrix gate below), and there is no downgrade path at all. `status_version` only increments on a *real* transition — a third, fourth, ... membership attaching to an already-`corroborating` topic touches neither field.

## 24. `record_topic_extraction_run` — parameters and provenance

Eighteen parameters mirror every `topic_extraction_runs` column the caller can legitimately supply; the RPC itself derives everything else server-side and accepts none of it from the caller:

- **`source_snapshot`/`source_snapshot_digest`** — built by re-reading the live `signal_evidence` row (by `p_signal_evidence_id`) and its `signal_sources` row (by `signal_evidence.signal_source_id`) inside the RPC. Canonical field order (fixed, hand-built via `format()` + `to_json()`, never a `jsonb_build_object(...)::text` cast — see §19's Shadow Topic precedent for why): `evidence_id, evidence_type, external_ref, title, snippet, published_at, canonical_url, first_seen_at, signal_source_id, source_type, source_external_id, source_family_key`. Every field is wrapped `coalesce(to_json(x)::text, 'null')` — `to_json(NULL)` returns SQL `NULL`, not the JSON literal `"null"`, which `format()`'s `%s` would otherwise substitute as an empty string and produce invalid JSON for any nullable column (`snippet`, `published_at`, `canonical_url`). Digest = `sha256` of that exact canonical text.
- **`normalized_input_digest`** — always `sha256(p_normalized_extraction_input)`, recomputed server-side regardless of what the caller believes it to be; there is no "trust the caller's digest" path.
- **`extraction_config_digest`** — `sha256` of a fixed-order canonical object: `extraction_method, normalization_version, extraction_schema_version, provider, model, prompt_version, deterministic_extractor_version` (exactly the field order the S2A contract §15 names).
- **`output_digest`** — only computed when `p_status='completed'`. **Canonicalization schema version 1** (S2B Final Canonical Digest Correction, superseding the original `p_structured_output::text` shortcut — Postgres's `jsonb::text` key order is a documented-behavior *implementation detail*, not a guaranteed public API, exactly the risk the Shadow Topic v0 contract already flags for `input_digest`, see §19). Explicit fixed field order, matching `topic_extraction_output_v1`'s own field order: `extraction_schema_version, canonical_phenomenon_label, label_language, subject_entities, action_or_event, location, temporal_context, specificity, content_format, confidence, supporting_spans`. Strings via `to_json()` (correct JSON escaping of quotes/backslashes/control characters/Unicode, including a literal `chr(31)` — the exact class of byte that made the *old* `decision_digest`'s `chr(31)`-delimited concatenation collision-prone, see below). Nullable string fields (`action_or_event`, `location`, `temporal_context`): SQL `NULL` → JSON `null` literal. **`confidence`**: cast to `NUMERIC(5,4)` then `::text` — a fixed 4-decimal-place form, so `0.85` and `0.8500` always canonicalize to the identical string `"0.8500"` (integration-tested). `subject_entities`: array order preserved (semantic order, not sorted), each element serialized via its own `jsonb::text` (already JSON-typed, so no double-encoding). `supporting_spans`: array order preserved (semantic citation order — reordering it changes the digest, tested), each span object rebuilt in a fixed `{source_field, quoted_text}` field order regardless of the original object's key order (key order does *not* change the digest, tested) — `WITH ORDINALITY` on `jsonb_array_elements` guarantees the aggregation preserves each array's original element order, since plain `string_agg` without an explicit `ORDER BY` does not guarantee that.
- **`confidence`** (the top-level `topic_extraction_runs` column) — derived as `(p_structured_output->>'confidence')::numeric` when completed, `NULL` when failed. Never a separate parameter; this keeps the top-level column and the nested `structured_output.confidence` a single source of truth instead of two values that could drift apart.

**Idempotency and cache semantics** (mirrors the `reserve_provider_units`/`run_shadow_topic_scoring` insert-then-catch pattern rather than a pre-`SELECT`, so genuine concurrent races resolve correctly without a `TOCTOU` window): the RPC always attempts the `INSERT` first, inside a `BEGIN...EXCEPTION WHEN unique_violation` block that inspects `GET STACKED DIAGNOSTICS ... CONSTRAINT_NAME` to tell the two possible collisions apart:
- **`topic_extraction_runs_idempotency_key_key`** — a whole-request digest (an explicit `to_json()`-escaped JSON-object canonical form over every semantically meaningful input field, fixed field names/order — **not** a `chr(31)`-delimited concatenation, since `provider`/`model`/`prompt_version`/`error_class` are free-text caller-supplied fields for `ai_assisted` extractions and could in principle contain a literal `chr(31)` byte, which would silently shift field boundaries and let two genuinely different requests collide onto the same digest; never a stored column, computed fresh on both sides for the comparison) is recomputed from the *stored* colliding row and compared against the *current call's* freshly computed one. Equal → `outcome:"replayed"`, returns the existing row. Different → `RAISE EXCEPTION` (idempotency-key reuse across a genuinely different request is a caller bug, not silently accepted).
- **`topic_extraction_runs_completed_cache_key`** (the S2A partial unique index on `(signal_evidence_id, normalized_input_digest, extraction_config_digest) WHERE status='completed'`) — a different idempotency_key hit the same completed-cache identity. Returns the existing completed row directly as `outcome:"cache_hit"`, never surfaces the raw constraint violation to the caller.
- A `failed` attempt never touches the completed-cache index (it isn't part of the partial index's `WHERE` clause), so failed retries under fresh `idempotency_key`s always insert a new row — exactly the "retry indefinitely" behavior §15 describes.

Two real concurrency scenarios are integration-tested (two truly separate `docker exec psql` processes, `Promise.all`, not simulated): two identical concurrent requests resolve to exactly one row with outcomes `{created, replayed}`; two concurrent requests sharing a completed-cache identity under different idempotency keys both succeed, resolving to exactly one completed row.

## 25. `record_topic_assignment_decision` — parameters, locking, and the atomic sequence

Six parameters: `p_extraction_run_id, p_outcome, p_decision_reason, p_deterministic_signals, p_idempotency_key, p_existing_semantic_topic_id` (the last required iff `ATTACH_EXISTING`, forbidden otherwise). The RPC re-reads `topic_extraction_runs` by `p_extraction_run_id` and requires `status='completed'` — `canonical_label`, `label_language`, `specificity`, and `confidence` are read **exclusively** from that row's persisted `structured_output`; the caller cannot supply redundant copies of any of them.

**Locking.** An evidence-level `pg_advisory_xact_lock(hashtextextended(signal_evidence_id::text, 0))` is taken immediately after re-reading the extraction (before any idempotency lookup or write) — since an `extraction_run_id` belongs to exactly one evidence, this alone serializes every concurrent call for the *same* extraction_run_id, making a plain pre-`SELECT` idempotency check (rather than the extraction RPC's insert-then-catch pattern) correct here: the second of two truly concurrent identical calls simply blocks on the lock until the first commits, then re-reads and correctly replays. For `ATTACH_EXISTING`, the target `semantic_topics` row is additionally locked with `SELECT ... FOR UPDATE` — this is the mechanism that serializes the *cross-evidence* race (two different evidences, hence two different advisory locks, both attaching to the same topic): the second transaction blocks at `FOR UPDATE`, then re-reads a fresh `lifecycle_status` after the first commits, guaranteeing the `candidate_singleton→corroborating` transition fires at most once even under real concurrency (integration-tested with two genuine concurrent processes).

**Idempotency.** `topic_assignment_decisions.extraction_run_id` is `UNIQUE` — the RPC's own idempotency check leans on this directly: `SELECT` by `extraction_run_id` first (not `idempotency_key`), and a `decision_digest` comparison decides replay-vs-mismatch exactly like the extraction RPC. **Canonicalization schema version 1** (S2B Final Canonical Digest Correction, superseding the original `chr(31)`-delimited concatenation — a caller-supplied `deterministic_signals` string value could contain a literal `chr(31)` byte, shifting field boundaries and colliding two genuinely different decisions onto the same digest, exactly the risk `output_digest` above already documents): an explicit `to_json()`-escaped JSON-object canonical form, fixed field order `extraction_run_id, outcome, decision_reason, deterministic_signals, existing_semantic_topic_id, idempotency_key`. `extraction_run_id`/`existing_semantic_topic_id`: `uuid::text` (Postgres's `uuid` type always renders lowercase canonical form on cast, regardless of input case — no separate lowercasing step needed). `existing_semantic_topic_id` SQL `NULL` (for `CREATE_NEW`/`QUARANTINE`) → JSON `null`.

**`deterministic_signals` canonical contract — S2B v0, closed for digest purposes.** The 073 `topic_assignment_decisions_deterministic_signals_is_object` CHECK only requires `jsonb_typeof=object` — no key set has ever been specified, and no S2B code path reads any key from it yet. Rather than trust Postgres's internal jsonb key ordering (the same documented-but-not-guaranteed-API risk as `output_digest` above) or invent a fixed named-key schema nothing has asked for, S2B v0 closes it minimally: **a flat object of scalar (string/number/boolean/null) values only** — a nested object or array value is rejected outright (`RAISE EXCEPTION`, tested for both nested-object and nested-array), not silently canonicalized ambiguously. Keys are sorted **lexicographically by byte order** (a plain SQL `ORDER BY` on the key text, computed by the RPC itself — not Postgres's internal storage order) via `jsonb_each(...) ORDER BY key`, each `"key":value` pair joined with `,`; values (already validated scalar) serialize via their own `jsonb::text` directly, since a bare scalar has no key-ordering ambiguity at all — only multi-key *objects* carry that risk. Widening this to nested structures, if a real future need arises, is a versioned schema change (`canonicalization schema version 2`), not a silent behavior change.

A separate check rejects `idempotency_key` reuse across a *different* `extraction_run_id` outright (a caller bug, not a legitimate retry pattern) — if this genuinely races (a realistic edge case, not one of the concurrency scenarios below), the resulting raw `unique_violation` is allowed to propagate and abort the whole calling transaction, which is exactly the "any intermediate error → full rollback" behavior required — no nested exception handling needed for that specific case since nothing had been written yet by the time it could fire.

Two same-`extraction_run_id` concurrency scenarios are integration-tested (two truly separate `docker exec psql` processes, `Promise.all`, not simulated, each promise individually caught since either process can legitimately be the one that loses the race): **(A)** identical payload + identical `idempotency_key` → exactly one topic/membership/decision/event, outcomes `{created, replayed}`, no raw `unique_violation` ever surfaces to either caller; **(B)** two different `idempotency_key`s racing on the same `extraction_run_id` (e.g. one call attempting `CREATE_NEW`, another concurrently attempting `QUARANTINE`) → at most one decision persists, the losing call's entire transaction rolls back with the controlled `"already has a decision with different parameters"` message (never a bare constraint-violation string), and zero orphan topic/membership/event rows result from the loser (verified by re-deriving what the loser's `CREATE_NEW` topic's `creation_request_digest` *would* have been and confirming no such row exists unreferenced).

**Outcome validation** (before any write):
| Outcome | `p_existing_semantic_topic_id` | `decision_reason` allowed | `structured_output` gate |
|---|---|---|---|
| `CREATE_NEW` | must be `NULL` | `no_similar_topic_found` only | `specificity='specific'` and `confidence >= 0.8500` |
| `ATTACH_EXISTING` | required | `exact_entity_match`, `embedding_similarity_match`, `manual_review_confirmed`, `manual_review_override` | `specificity='specific'` and `confidence >= 0.8500` |
| `QUARANTINE` | must be `NULL` | `malformed_extraction`, `below_confidence_threshold` | none — QUARANTINE is the app's escape hatch precisely *for* low-confidence/non-specific extractions |

**ATTACH-matrix** (target topic `lifecycle_status` vs. what's allowed) — the S2 design decision from the prior handover, now implemented and tested: `candidate_singleton`/`corroborating`/`coherent` accept any of the four `ATTACH_EXISTING` `decision_reason`s automatically; `ambiguous` accepts only `manual_review_confirmed`/`manual_review_override` (`RAISE EXCEPTION` otherwise); `split_required`/`merge_candidate`/`superseded`/`archived` reject `ATTACH_EXISTING` unconditionally, regardless of `decision_reason` — including `manual_review_override`, tested explicitly.

**`decision_reason` → `assignment_reason`/`event_reason` mapping** (identical for both — `semantic_topic_membership.assignment_reason` and `semantic_topic_membership_events.event_reason` always carry the same value for a given decision): `exact_entity_match→entity_event_match`, `embedding_similarity_match→embedding_similarity`, `manual_review_confirmed→manual_review_confirmed`, `manual_review_override→manual_review_override`, and `CREATE_NEW`'s single reason `no_similar_topic_found` always produces `topic_creation_seed` (the S2A-added fifth enum value, §18 — this RPC is the reason it exists).

**Atomic sequence**, exactly as specified and tested: lock(s) → re-read extraction + idempotency check → contract validation → topic create (`CREATE_NEW`) or target topic lock+validate (`ATTACH_EXISTING`) or neither (`QUARANTINE`) → membership insert (skipped for `QUARANTINE`) → lifecycle transition check (`ATTACH_EXISTING` only) → decision insert → event insert (skipped for `QUARANTINE`) → return. `semantic_topics.creation_request_digest` (required `UNIQUE NOT NULL` by the 072 schema) is set to `sha256(extraction_run_id || 'topic_creation_seed')` for `CREATE_NEW` — deterministic and trivially unique because `topic_assignment_decisions.extraction_run_id` is itself `UNIQUE`, so at most one `CREATE_NEW` can ever exist per extraction run; no client-supplied content is needed or accepted for it.

## 30. Canonical input timestamp v2 (`normalization_version` 1 → 2)

**v1 limitation (discovered during the first real production shadow extraction, `extraction_run_id` `c5e4da64-7e23-4e56-9620-6cdcafb395d5`, `normalization_version=1`):** `normalized_extraction_input` embedded `signal_evidence.published_at` exactly as whatever string the caller's data source produced, with no canonicalization. Postgres's own `::text` cast on a `timestamptz` ("2026-07-26 04:47:43+00" — space-separated, colon-less offset) and Postgres's `to_json()`/`to_jsonb()` convention, which PostgREST (and therefore `@supabase/supabase-js`, the only real caller so far) relies on to serialize the identical column ("2026-07-26T04:47:43+00:00" — "T"-separated, colon offset), disagree on format. Empirically, four representations of one instant produced four different `normalized_input_digest` values. Because `topic_extraction_runs_completed_cache_key` and 075's global attempt-limit are both keyed on `normalized_input_digest`, a future caller using a different timestamp-serialization code path for the same evidence could have bypassed both guards and triggered an uncontrolled second real provider call/cost for a semantically duplicate request. §15's own wording already flagged the shape of this risk ("the digest is at least self-consistent, though it cannot prove the normalization *process* was correct") — this section closes the gap that sentence anticipated.

**v2 canonical format:** `YYYY-MM-DDTHH:mm:ss.sssZ` — always UTC, always `T`, always exactly 3 millisecond digits (**truncated**, never rounded, from any finer source precision), always `Z`. Two strings denoting the same instant, in any accepted input shape, always canonicalize to byte-identical output.

- **TypeScript** (`lib/semantic-topic/canonical-timestamp.ts`, `canonicalizeTimestamp()`): never calls `new Date(someString)` (ECMA-262 only guarantees a specific parse for the exact shape `toISOString()` itself produces, not the RFC 3339 / Postgres-native variety this contract must accept) — extracts fields via an explicit regex, then combines them with `Date.UTC(...)`, whose *arithmetic* is fully spec-guaranteed. `null` passes through as `null`; anything unparseable or out-of-range (invalid calendar date, hour/minute/second out of range) throws (fail-closed).
- **SQL** (`record_topic_extraction_run` AND `reserve_ai_provider_units`, both migration 076 — the identical expression duplicated in each, matching this codebase's established per-RPC-inlining convention rather than a shared helper with its own hash-gate governance): `to_char(ts AT TIME ZONE 'UTC', 'YYYY-MM-DD"T"HH24:MI:SS.MS"Z"')` — explicit UTC conversion plus explicit format string, independent of session `TimeZone`/`DateStyle` (empirically verified under `SET DateStyle='German, DMY'` and `SET timezone='Asia/Tokyo'`). Postgres's `MS` format specifier truncates, matching the TypeScript side exactly (verified against a 12-case precision/offset/rollover matrix on both sides — byte-identical results).
- `SEMANTIC_TOPIC_NORMALIZATION_VERSION` (embedded in `extraction_config_digest`) bumped `1 → 2` to mark this as a versioned normalization-algorithm change, not a silent v1 patch — v1 rows are never reinterpreted as v2.

**Reproducibility contract, v1 vs v2:** a v2 `topic_extraction_runs` row's `normalized_input_digest` **is** independently reproducible from its own stored `source_snapshot.published_at` alone (migration 076 also corrected `source_snapshot`'s `published_at`/`first_seen_at` fields to the same canonical format, so the two now agree). A **v1** row's `normalized_input_digest` is reproducible only from the *actual* text the v1 caller built (which used the caller's own raw serialization) — reconstructing it from the v1 row's own stored `source_snapshot.published_at` (SQL `::text` format) gives a *different*, wrong digest. This is the precise, permanent, documented v1 limitation; `output_digest` and `extraction_config_digest` are unaffected on both sides (neither embeds a timestamp).

**Scope of the 076 fix (revised — see "Final Server Enforcement" below for why the first pass was insufficient):** `record_topic_extraction_run`'s `source_snapshot` construction, AND `reserve_ai_provider_units`'s digest computation. `record_topic_assignment_decision` (074's other RPC) never references `published_at`/`first_seen_at` — untouched. The other five 075 RPCs (`mark_ai_provider_attempt_started`, `commit_ai_provider_units`, `mark_ai_provider_outcome_unknown`, `release_ai_provider_units`, `finalize_ai_provider_reservation_outcome`, `reconcile_stale_ai_provider_reservations`) never reference `signal_evidence` or a timestamp-bearing digest input at all — audited, untouched.

**Final server enforcement (why `reserve_ai_provider_units` alone hashing "whatever text the caller built" was not enough):** the first pass of this fix corrected only `record_topic_extraction_run`'s *stored* `source_snapshot`, reasoning that `reserve_ai_provider_units` "only hashes whatever `normalized_extraction_input` text the caller already built." That is true, but insufficient: since `topic_extraction_runs_completed_cache_key` and the global attempt-limit are both keyed on `normalized_input_digest`, a caller that built its own non-canonical (or tampered, or stale) `normalized_extraction_input` and called `reserve_ai_provider_units` directly could still mint a real, fee-incurring reservation under a digest the TypeScript layer would never have produced — bypassing the cache/attempt-limit guard the canonical format exists to protect. `reserve_ai_provider_units` (076-corrected) now re-reads the live `signal_evidence` row by `p_signal_evidence_id` and rebuilds the canonical `normalized_extraction_input` itself, byte-for-byte identical to TypeScript's `buildNormalizedExtractionInput` (title always, whitespace-collapsed; snippet only if non-blank, whitespace-collapsed; `published_at` only if non-null, the canonical timestamp above; `canonical_url` only if non-blank, trimmed but not whitespace-collapsed — each field on its own line, joined by `\n`, in exactly that order, no field emitted for a null/blank source value). The caller-supplied `p_normalized_extraction_input` is compared against this server-rebuilt text and **rejected on any mismatch, before any budget/reservation DML** — the RPC signature is unchanged (no new overload), the caller-supplied value is still accepted as a parameter and still hashed to produce `normalized_input_digest`, but only after being proven byte-identical to the server's own reconstruction. This closes the gap end-to-end: `record_topic_extraction_run` alone only fixed what got *stored*; `reserve_ai_provider_units`'s own rebuild-and-compare is what stops a non-canonical digest from ever being paid for in the first place. Migration 076's fail-closed hash-gate now covers both RPCs together, in one transaction: both legacy → replace both; both corrected → no-op; anything else (including one-of-each "mixed" state) → `RAISE EXCEPTION`, neither function touched.

**The v1 production row is immutable** — `c5e4da64-7e23-4e56-9620-6cdcafb395d5`, `normalization_version=1`, permanently distinguishable from any v2 row by that column alone, never updated/deleted/backfilled/reinterpreted by this or any future migration.

## 31. Human-Reviewed Candidate Workflow — schema foundation (migration 077)

**Status: schema only, no RPCs, no rollout.** Migration 077 adds four new, still-writerless tables (`semantic_topic_reviewers`, `semantic_topic_reviewer_events`, `topic_assignment_review_requests`, `topic_assignment_review_events`) and one additive `decision_reason` CHECK bump on the existing `topic_assignment_decisions` table (`human_review_approved`, `human_review_rejected` — two new values, the seven existing ones untouched). **Nothing in this migration is callable yet** — the actual `create_topic_assignment_review_request`, `record_topic_assignment_review_decision`, `execute_approved_topic_assignment_review`, and `expire_stale_topic_assignment_review_requests` RPCs are the scope of a **separate, future, explicitly-approved migration 078**. All four new tables: RLS enabled+forced, 0 policies, `service_role` **SELECT only**, no grant to `anon`/`authenticated`/`PUBLIC` — no application code path can write a row today, exactly the same structural guarantee 072's S1 tables established for `semantic_topics`/`semantic_topic_membership`.

**The existing `record_topic_assignment_decision` (074) is completely unmodified** — body hash `759de5ab474c9a7aa105564ca95541cc`, six-parameter signature, grants, and the `0.8500` automatic `CREATE_NEW`/`ATTACH_EXISTING` confidence threshold are all byte-identical to before 077. The RPC's own internal `decision_reason` validation (`IF p_decision_reason NOT IN (...) THEN RAISE EXCEPTION`, hardcoded inside the function body, independent of the table CHECK) still rejects `human_review_approved`/`human_review_rejected` for every outcome — this is **expected and correct**: the two new reason values exist at the table level so that the future 078 executor RPC can `INSERT` them directly (bypassing 074's own outcome-validation gate entirely, matching this codebase's established per-RPC-inlining/duplication convention rather than routing through the old RPC), not so that a caller of the *unmodified* 074 RPC could use them.

**Human approval is never a caller-supplied boolean or free-text claim.** `topic_assignment_review_requests` carries a full structured review snapshot (`canonical_topic_label`, `topic_definition`, `scope`, `inclusion_criteria`, `exclusion_criteria`, `lane_neutral_confirmed IS TRUE`, `evidence_adequacy='adequate'`, `duplicate_search_outcome`, `proposed_outcome`, `target_semantic_topic_id`, `uncertainty_classification`, `reviewer_rationale`, `review_policy_version`) — every field required, via explicit `IS NULL`/`IS NOT NULL`/`IS TRUE`/`IS DISTINCT FROM` CHECKs (never a bare comparison a SQL `NULL` could silently pass), before a row may reach `status='approved'`.

**State machine:** `pending → {approved | rejected | expired | cancelled}`, `approved → {executed | revoked}`. Each status has its own field-completeness CHECK (`..._pending_fields_empty`, `..._approved_fields_required`, `..._rejected_fields_required`, `..._expired_fields_empty`, `..._cancelled_fields`, `..._revoked_fields`, `..._executed_fields`). **Corrected from the prior design draft:** `revoked` and `executed` **preserve** the full original approval snapshot including `approval_digest`/`approval_digest_version` — only the status and the revoke/execute marker fields change; a revoked approval's judgment record is never erased. **Human rejection is terminal in the v0 design**: a `rejected` row requires a filled `resulting_decision_id` (the append-only `QUARANTINE` row the future 078 executor writes atomically in the same call as recording the rejection, `decision_reason='human_review_rejected'`) — `topic_assignment_decisions.extraction_run_id UNIQUE` then permanently closes that extraction run to any further generation, exactly as it already does for the two existing production `QUARANTINE` decisions. Only `expired`/`cancelled`/`revoked` (which never produce a decision) leave the run open for a new `generation` — enforced by the partial unique index `... WHERE status IN ('pending','approved')` (one live request per run) plus, in 078, an RPC-level invariant that a new request cannot be created once `topic_assignment_decisions` already has a row for that run — this cross-table rule is deliberately **not** attempted as a CHECK constraint (a schema-only migration cannot safely express it; documented here as a 078 RPC responsibility instead).

**Idempotency storage — three separate phase-scoped key/digest pairs**, each its own column pair, so a duplicate key value in one phase can never collide with the same value used in a different phase: `request_idempotency_key`/`request_operation_digest` (UNIQUE), `decision_idempotency_key`/`decision_operation_digest` (partial UNIQUE, `WHERE decision_idempotency_key IS NOT NULL`), `execution_idempotency_key`/`execution_operation_digest` (partial UNIQUE, `WHERE execution_idempotency_key IS NOT NULL`). The actual replay/idempotency *behavior* (insert-then-catch vs. state-based replay, per operation) is a 078 RPC contract, not expressible at the schema level alone — this migration only guarantees the storage and uniqueness scope is physically correct.

**Expiry is not attempted as a same-transaction write-then-raise.** A Postgres function call does **not** run in its own sub-transaction — a `RAISE EXCEPTION` after an `UPDATE` in the same call rolls back that `UPDATE` too. 077 only prepares the `expires_at` column; the actual sweeper (`expire_stale_topic_assignment_review_requests`, its own RPC, its own transaction, `WHERE status='pending' AND expires_at <= statement_timestamp()`) and the decide-path's read-only (no write attempt) expiry check are both 078 scope, documented here so the eventual implementation does not repeat the transaction-semantics mistake an earlier draft of this design made.

**Reviewer authorization** is a separate, narrow allowlist (`semantic_topic_reviewers`) — the existing `profiles` table has no role/admin concept at all (audited: zero `isAdmin`/`is_admin`/`ADMIN_*` hits anywhere in the codebase) and was deliberately not reused for this. `semantic_topic_reviewer_events` is the append-only audit trail for `granted`/`deactivated`/`reactivated` transitions, separate from `topic_assignment_review_events` (the append-only audit trail for request-lifecycle transitions) — the two event tables are never merged. **No real reviewer is bootstrapped by 077** — the migration text contains no `INSERT` into `semantic_topic_reviewers` and no real Supabase user UUID; the actual owner-reviewer bootstrap is a separate, manual, `postgres`-privileged, explicitly-approved production step, out of scope for both 077 and 078.

**ATTACH_EXISTING is supported in v0**, human-selected (the reviewer picks an existing `semantic_topic_id` directly — no embedding infrastructure), via `target_semantic_topic_id` plus the `..._create_new_no_target`/`..._attach_requires_target` conditional CHECKs. The future 078 executor is responsible for re-locking and re-validating the target topic's `lifecycle_status` **at execution time**, not just at decide time (documented as an RPC concern, not schema-expressible).

**Approval digest** — algorithm/domain-separator/canonical-serialization details (explicit domain-separator strings, not just a bare version integer; `to_json()`-escaped fixed field order; UUID lowercase; canonical UTC millisecond timestamps; NULL→JSON `null`) are a 078 RPC contract; 077 only provides the `approval_digest`/`approval_digest_version` storage columns.

## 32. Human-Reviewed Candidate Workflow — RPC layer (migration 078)

**Status: local only, not deployed to production.** Migration 078 adds eight `SECURITY DEFINER` RPCs on top of 077's schema — no new tables, no `ALTER` on 001–077, `record_topic_assignment_decision` (074) and the `0.8500` automatic threshold remain byte-identical (proven by the same final self-check pattern 077 used, hash `759de5ab474c9a7aa105564ca95541cc`). No reviewer-provisioning/deactivation RPC exists yet — `semantic_topic_reviewers` is still populated only by manual, `postgres`-privileged `INSERT` (test fixtures in this repo do this; the real production bootstrap remains a separate, future, explicitly-approved step).

**The eight RPCs, callers, and state transitions:**

- **`create_topic_assignment_review_request(p_extraction_run_id, p_idempotency_key)`** — `service_role` only. Takes the evidence advisory lock (`hashtextextended(evidence_id, 0)`), re-reads the extraction post-lock, requires `status='completed'`, `specificity='specific'`, `confidence < 0.8500`, and ≥1 `supporting_spans` entry; rejects if `topic_assignment_decisions` already has a row for the run. `generation` is server-computed as `MAX(generation)+1` scoped to the run, but only *after* an idempotency-key lookup finds no existing row — computing it unconditionally would inflate the count on a replay of the very row being replayed against, producing a spurious digest mismatch (a real bug caught during implementation testing). Writes `pending` + a `requested` event atomically. Idempotent: same key + same payload → replay; same key + different extraction_run → `IDEMPOTENCY_KEY_REUSE`; the one-live-request-per-run partial unique index is the ultimate concurrency backstop, caught via `EXCEPTION WHEN unique_violation` on `GET STACKED DIAGNOSTICS CONSTRAINT_NAME`, never a raw constraint-violation leak.
- **`list_pending_topic_assignment_review_requests(p_limit, p_after_requested_at, p_after_id)`** — `authenticated` only (no `service_role`/`anon` grant). Requires `auth.uid() IS NOT NULL` and an active `semantic_topic_reviewers` row for that `user_id`. `STABLE`, keyset-paginated (`requested_at, id`), `p_limit` clamped to `[1,50]`. Returns only a data-minimized projection — candidate label/specificity/content_format/model-reported confidence/supporting spans/evidence+source summary — never the raw `provider`/`model`/`prompt_version` or any secret.
- **`get_topic_assignment_review_request(p_review_request_id)`** — same authorization rule, single-request detail view, same data-minimization discipline; includes the decision snapshot once decided.
- **`record_topic_assignment_review_decision(...)`** — `authenticated` only. Reviewer identity is *always* `auth.uid()` — there is no `p_reviewer_user_id` or `p_reviewer_role` parameter, so a forged reviewer field is structurally impossible, not just validated away. Lock order: evidence (`tag 0`) → request (`tag 10`) → `SELECT ... FOR UPDATE`, matching the order already established in 074. `approved` requires the *complete* structured snapshot (`lane_neutral_confirmed IS TRUE`, `evidence_adequacy='adequate'`, all judgment fields `NOT NULL`) and, for `ATTACH_EXISTING`, a decision-time target-lifecycle check (re-checked again at execution). `rejected` requires only its own minimal field set and, in the *same transaction*, directly `INSERT`s an append-only `topic_assignment_decisions` row (`outcome='QUARANTINE'`, `decision_reason='human_review_rejected'`, `idempotency_key='review-reject:'||review_request_id`) using 074's own canonical `decision_digest` text form for table-wide self-consistency — it does **not** call the unmodified 074 RPC (proven by a dedicated regression test: 074's own internal reason-matrix still correctly rejects `human_review_rejected`, exactly as expected). An expired-but-not-yet-swept request returns a controlled `REVIEW_REQUEST_EXPIRED` — the call never persists the expiry itself, matching 077's "no write-then-raise" design note; expiry persistence is exclusively the sweeper's job. Digest replay: same `decision_idempotency_key` + same recomputed digest → replay; same key + different payload → `IDEMPOTENCY_KEY_REUSE`; a fresh key against an already-decided request → `ALREADY_DECIDED`.
- **`expire_stale_topic_assignment_review_requests(p_batch_limit)`** — `service_role` only. A single `UPDATE ... FROM (SELECT ... FOR UPDATE SKIP LOCKED)` CTE, `status='pending' AND expires_at <= statement_timestamp()`, `p_batch_limit` clamped to `[1,500]`, one `expired` event per row, genuinely idempotent (a second run finds nothing left to expire) — no write-then-raise anywhere in the function.
- **`cancel_topic_assignment_review_request(p_review_request_id)`** — **corrected during the Security and Concurrency Closure gate.** The original two-parameter shape (`p_review_request_id, p_cancelled_by_user_id`) let a `service_role` caller supply an *arbitrary* `auth.users` UUID as the audit identity — an unforgeable-looking but actually-forgeable claim, no different in kind from letting a caller self-report reviewer identity elsewhere in this workflow (which every other RPC here deliberately forbids). The floated "drop the parameter, keep `service_role`, hardcode `actor_user_id=NULL`" fix is **provably inapplicable**: 077's own `topic_assignment_review_requests_cancelled_fields` CHECK requires `cancelled_by_user_id IS NOT NULL` whenever `status='cancelled'`, and 077 must never be altered — there is no real, non-invented `auth.users` row to attribute a bare `service_role` cancel to. The only fail-closed option that (a) never trusts a caller-supplied identity and (b) always has a real, valid `auth.users` FK to write is to make cancellation `authenticated`+active-reviewer, `cancelled_by_user_id` coming exclusively from `auth.uid()` — exactly the pattern already proven safe by `revoke_topic_assignment_review_approval`. Cancel and revoke are now symmetric: cancel calls off a `pending`-but-not-decided request, revoke calls off an `approved`-but-not-executed one; both are equally reviewer-authenticated, equally `auth.uid()`-derived, equally forgery-proof. Only a `pending` request is cancellable; a repeat call on an already-`cancelled` row replays (state-based idempotency — 077 carries no `cancel_idempotency_key` column); any other terminal/live status is a controlled `REVIEW_REQUEST_NOT_CANCELLABLE`. Logical status change only, never a physical `DELETE`. Proven via a dedicated PostgREST-ambiguity test: exactly one overload of this function name exists, in both `pg_proc` and `information_schema.routines`, after the old two-parameter signature was explicitly, individually `DROP`ped (verified target, no wildcard, no `CASCADE`) from the local dev DB before the corrected migration was reapplied from a clean 0-of-8 topology.

**Reviewer-authorization TOCTOU closure**: every mutation RPC that gates on `active=true` (`record_topic_assignment_review_decision`, `cancel_topic_assignment_review_request`, `revoke_topic_assignment_review_approval`, `execute_approved_topic_assignment_review`) now takes that check via `SELECT ... FOR SHARE` rather than a plain read. Under plain READ COMMITTED semantics, a concurrent deactivation could otherwise commit *after* the check but *before* this call's own commit, letting a call proceed on since-invalidated authorization. `FOR SHARE` only locks a row that actually matches the `active=true` filter (an already-inactive reviewer's row is never touched, so it never blocks anything), and forces a genuinely concurrent deactivating `UPDATE` on that same row to wait until this transaction resolves — whichever transaction reaches the row first determines the (always self-consistent) outcome. No other RPC in this codebase ever locks `semantic_topic_reviewers`, so this introduces no new deadlock surface.

**Global lock order** (audited across every 072–078 RPC that can touch `signal_evidence`, `topic_assignment_decisions`, `semantic_topic_membership`, semantic-topic lifecycle, or `topic_assignment_review_requests`):

| RPC | Lock order |
|---|---|
| `record_topic_assignment_decision` (074) | evidence advisory (`hashtextextended(evidence_id, 0)`) → target `semantic_topics` row `FOR UPDATE` (ATTACH_EXISTING only) |
| `create_topic_assignment_review_request` (078) | evidence advisory (`tag 0`) |
| `record_topic_assignment_review_decision` (078) | evidence advisory (`tag 0`) → request advisory (`hashtextextended(review_request_id, 10)`) → request row `FOR UPDATE` → reviewer row `FOR SHARE` (ATTACH_EXISTING target: read-only pre-check, no lock — the executor re-locks it) |
| `cancel_topic_assignment_review_request` (078) | reviewer row `FOR SHARE` → request advisory (`tag 10`) → request row `FOR UPDATE` |
| `revoke_topic_assignment_review_approval` (078) | reviewer row `FOR SHARE` → request advisory (`tag 10`) → request row `FOR UPDATE` |
| `expire_stale_topic_assignment_review_requests` (078) | request rows `FOR UPDATE SKIP LOCKED` only (batch, no advisory lock — SKIP LOCKED means it never waits on a row another RPC is holding) |
| `execute_approved_topic_assignment_review` (078) | evidence advisory (`tag 0`) → request advisory (`tag 10`) → request row `FOR UPDATE` → reviewer row `FOR SHARE` → target `semantic_topics` row `FOR UPDATE` (ATTACH_EXISTING only) |

Every RPC that touches both the evidence-scoped advisory lock and the request-scoped one takes them in the same order (evidence → request), and every RPC that touches both the request row and a target-topic row takes them in the same order (request → topic) — so no two of these RPCs can ever hold locks in reverse order relative to each other, which is what a deadlock cycle would require. `record_topic_assignment_decision` (074, unmodified) shares the *exact same* evidence-advisory-lock tag/namespace as all evidence-touching 078 RPCs, which is what correctly serializes a direct 074 QUARANTINE call against a concurrent `create`/`execute` on the same evidence (proven by dedicated concurrency tests) rather than leaving them free to race independently. No other 001–078 RPC (Creator Lane's `067` reclassification locks, `070`/`071` Shadow Topic scoring locks, `075`'s AI-quota reservation locks, `061`/`063`/`066`'s provider-budget-reservation locks) ever touches `signal_evidence`, `topic_assignment_decisions`, `semantic_topics`, `semantic_topic_membership`, or `topic_assignment_review_requests` — zero shared lock surface, hence zero possible cross-feature deadlock cycle with any of them.
- **`revoke_topic_assignment_review_approval(p_review_request_id)`** — `authenticated`, active reviewer, `auth.uid()`-derived actor. Only an `approved`-and-not-yet-`executed` request is revocable; **any** currently-active reviewer may revoke, not only the original approver (the spec did not restrict this, and v0 is a single-owner-reviewer closed beta where the distinction is moot). Repeat revoke replays (state-based); an `executed` request can never be revoked (proven by test). The approval snapshot, including `approval_digest`, is left untouched — only `status`/`revoked_at`/`revoked_by_user_id` change, per 077's `revoked_fields` CHECK.
- **`execute_approved_topic_assignment_review(p_review_request_id, p_idempotency_key)`** — `service_role` only, an entirely new RPC (no overload, no wrapper, no signature change on 074). Lock order: evidence (`tag 0`) → request (`tag 10`) → `FOR UPDATE`, then (`ATTACH_EXISTING` only) target topic `FOR UPDATE`. Re-reads and recomputes, then *compares*, both `request_payload_digest` (from the extraction's current `output_digest`/`confidence`/`specificity`) and `approval_digest` (from the request's current stored judgment fields) against what is stored — any drift between approval time and execution time is fail-closed, not assumed away. Also re-checks the reviewer is *currently* `active=true` (a reviewer deactivated between approval and execution blocks execution, proven by test) and that `review_policy_version`/`approval_digest_version` are within the supported set (`=1`). `CREATE_NEW` inserts `semantic_topics` (`creation_request_digest` seeded from `review_request_id || chr(31) || 'human_review_topic_creation_seed'`, the same delimiter-based pattern 074 already uses for its own seed digest) + membership + `topic_assignment_decisions` (`decision_reason='human_review_approved'`) + `semantic_topic_membership_events`, all in 074's own canonical forms so the tables stay self-consistent regardless of which RPC wrote a given row. `ATTACH_EXISTING` re-validates the target's lifecycle under lock (same forbidden-state list as 074 — `split_required`/`merge_candidate`/`superseded`/`archived` — but **not** `ambiguous`: a human explicitly selected this exact target during review, which *is* the manual confirmation 074 otherwise requires a `manual_review_*` reason for) and reuses 074's own `candidate_singleton → corroborating` transition logic verbatim. Both paths write `assignment_reason='manual_review_confirmed'` and a distinct `algorithm_version=2` (vs. 074's `1`), so a membership's provenance — automated S2B match vs. human-reviewed workflow — stays queryable from the row itself. Execution replay follows the same key/digest pattern as decision replay (`ALREADY_EXECUTED` for a fresh key on an already-`executed` row).

**Digest contract — three domains, each the literal first element of its canonical text** (not just a version-label comment): `willviral.semantic-topic.review-request:v1`, `willviral.semantic-topic.review-decision:v1`, `willviral.semantic-topic.review-execution:v1`. All digests: SHA-256, UTF-8, lowercase hex, a fixed-field-order JSON-object *text* built via `format()` + `to_json()` (proper string escaping, SQL `NULL`→JSON `null`), never delimiter-based concatenation for any field that could itself contain the delimiter. `request_payload_digest` deliberately wraps the extraction's own already-canonical `output_digest` (074's structured-output digest) rather than re-deriving a second, potentially-divergent canonicalization of the same JSON. `approval_digest` is idempotency-key-free by design — it covers the full reviewer judgment plus `request_payload_digest`, and is exactly what the executor recomputes later; `decision_operation_digest` is `approval_digest`'s content *plus* the call-specific `decision_idempotency_key`, cleanly separating "proof of what was approved" (long-lived, re-derivable) from "proof this exact RPC call happened" (idempotency-scoped only).

**Security posture**: every RPC — explicit `postgres` owner, `SECURITY DEFINER`, `SET search_path = public, pg_temp`, `REVOKE ALL FROM PUBLIC, anon, authenticated, service_role` followed by exactly one `GRANT EXECUTE`. **Corrected during the Security and Concurrency Closure gate**: the authorization split is `service_role` for exactly three system-driven RPCs (`create_topic_assignment_review_request`, `expire_stale_topic_assignment_review_requests`, `execute_approved_topic_assignment_review`) and `authenticated` (active reviewer) for exactly five reviewer-facing ones (`list_pending_topic_assignment_review_requests`, `get_topic_assignment_review_request`, `record_topic_assignment_review_decision`, `cancel_topic_assignment_review_request`, `revoke_topic_assignment_review_approval`) — `cancel` moved from the original 4+4 split into the reviewer-facing group specifically because its original `service_role`-callable, caller-supplied-identity shape was a forgeable-audit-trail gap; see the closure section below. All splits proven via `has_function_privilege` VALIDATE-branch checks on every migration run, both directions. All four 077 tables remain `service_role` SELECT-only with zero direct-DML grants for *any* role, proven by dedicated `SET ROLE` tests in the 078 suite — every write happens exclusively through these eight RPCs. `service_role` cannot self-provision a reviewer (no such RPC exists in this migration).

**Concurrency**: proven with real parallel `psql` connections (not simulated) — two concurrent `create` calls on the same run (exactly one row survives), two concurrent reviewer decisions on the same request (exactly one wins), two concurrent executors on the same approved request (exactly one topic/membership/decision survives), and a decision-vs-expiry race (expiry only ever touches `status='pending'` rows, so a request that got decided first is simply skipped by the sweeper, never double-written).

**Extraction pipeline hook** — `lib/semantic-topic/human-review-extraction-hook.ts`, `maybeRequestHumanReview()`: a **sibling** function to `runShadowExtraction()` (`extraction-service.ts`), not a modification of it — `runShadowExtraction()`'s own internals, return shape, and error paths are completely untouched, so flag=false behavior is structurally byte-identical (this function short-circuits before any read or RPC call the instant the flag is false). ## 34. Human-Reviewed Candidate Workflow — Application Integration Closure (live orchestration + server-only boundary)

**Status: local application code only** — same production posture as §33 (no deploy, no reviewer bootstrap, no permanent flag enablement, no reviewer UI). This phase closes the two gaps §33 explicitly deferred: (1) `maybeRequestHumanReview()` is now actually called from inside the real extraction path, and (2) the service-role module is now a genuine build-time boundary, not just a documented convention.

**Call-graph audit finding (why the hook lives inside `runShadowExtraction()`)**: a full repository audit — not an assumption carried over from §33 — confirmed that `runShadowExtraction()` (`lib/semantic-topic/extraction-service.ts`) has **no application-level caller anywhere in this codebase**: not a cron route, not an API route, not a worker. The collector subsystem (`lib/emerging-signal/*`) and the semantic-topic extraction subsystem (`lib/semantic-topic/*`) remain two disconnected islands; neither imports the other, and no orchestrator — live, commented-out, or stubbed — connects collector → extraction → assignment anywhere in this repository. `record_topic_assignment_decision` likewise still has no application-level caller; only the felügyelt pilot scripts used throughout this rollout invoke it manually. Given that, `runShadowExtraction()` itself is the only thing in this codebase that represents "extraction completion" — there is no separate, external orchestration layer to hook into instead. `maybeRequestHumanReview()` is therefore called from inside `runShadowExtraction()`, in **both** of its terminal branches:

- the `completed` branch (a fresh extraction just finished), and
- the `cache_hit` branch (an identical prior extraction is being replayed).

The `cache_hit` branch call was not part of the original design and was found missing only by the mandated live E2E test ("same orchestration retried") — the second, identical call returned `cache_hit`, not `completed`, and without this fix a review request would never be requested for any extraction whose evidence+config combination had already been extracted once. This is documented here as a concrete example of why this gate's "prove via full local E2E, not assumption" requirement mattered: it caught a design gap that unit tests mocking the RPC layer could not have caught.

**Flag=false behavior (unchanged, verified byte-identical)**: `maybeRequestHumanReview()` short-circuits to `{ outcome: 'disabled' }` before any read or RPC call the instant `SEMANTIC_TOPIC_HUMAN_REVIEW_ENABLED` is not the literal string `'true'`. Every existing field on `ShadowExtractionResult` (`reservationId`, `extractionRunId`, `structuredOutput`, `capBreach`) is computed exactly as before this integration existed; the only change is one new, additive `humanReview` field on both the `completed` and `cache_hit` result shapes.

**Flag=true behavior — the orchestration contract**. `HumanReviewOrchestrationResult` (`lib/semantic-topic/human-review-extraction-hook.ts`) is a closed, exhaustive discriminated union — never free-text branching:

| Outcome | Meaning | Caller's correct next step |
|---|---|---|
| `disabled` | Flag is off | continue as today (no-op) |
| `created` | Fresh pending review request just created on this run | stop — no automatic QUARANTINE/assignment on this run, no automatic execution |
| `replayed` | Idempotent replay of an identical prior create call on this exact run | stop — same as `created`, no second request |
| `pending` | A live (pending/approved) review request already exists on this run | stop — the existing request is authoritative, never a second one |
| `not_eligible` | Genuinely ineligible (confidence ≥ 0.8500, non-specific, or zero supporting spans) — the RPC's own eligibility gate is the single source of truth, never duplicated at the application layer | continue whatever the existing, contractual assignment/QUARANTINE process would otherwise do — unchanged, no new reason value invented |
| `already_assigned` | This run already has a terminal `topic_assignment_decisions` row (from any source — an executed review, or a direct 074 QUARANTINE call) | idempotent no-op — never attempt a second request or decision |
| `retryable_failure` | A transient RPC/DB failure (`database_error`, `invalid_rpc_response`, or any other non-`not_eligible` failure shape) | fail-closed — the completed extraction remains safely retryable; never silently convert this into a terminal QUARANTINE decision |

The RPC's single generic `not_eligible` failure message is re-classified client-side into the three semantically distinct cases the contract needs, purely by matching the exact message text `create_topic_assignment_review_request` already produces (never a new RPC-side reason value): `/already has a topic_assignment_decisions row/` → `already_assigned`; `/already has a live \(pending\/approved\)/` → `pending`; anything else → the genuine `not_eligible`. The `0.8500` threshold, specificity check, and supporting-span requirement are still not duplicated as a second business decision anywhere in the application layer.

**Idempotency**: `deriveHumanReviewIdempotencyKey(extractionRunId)` returns the fixed-prefix key `` `human-review-request:${extractionRunId}` `` — deterministic per run, disjoint from every other domain's key namespace (`:quota`, `:extraction-run`, `review-reject:`), so a retry of the same extraction run always replays instead of erroring or double-creating.

**Live local E2E (real local Supabase stack, Anthropic provider mocked, `tests/human-review-app-integration.test.ts`)** — six scenarios, all passing, exercising the real `runShadowExtraction()` → `maybeRequestHumanReview()` → RPC → DB path:

1. flag=false: a completed extraction makes zero review-RPC calls, old behavior unchanged.
2. flag=true, eligible sub-threshold extraction: the live orchestration automatically creates a pending review request; a `requested` event exists; no `topic_assignment_decisions` row, no semantic topic, no membership; the reviewer list/get routes see the request.
3. the same orchestration retried: no second request, no second `requested` event — the second call legitimately lands on either `completed` or `cache_hit` (an identical retry is expected to hit the extraction cache), and either way `humanReview` resolves to `replayed`/`pending` rather than a fresh `created`.
4. an ineligible extraction: no review request is created; the pre-existing assignment/QUARANTINE path is left untouched.
5. a transient review-RPC failure (a genuinely unreachable Postgres client): no QUARANTINE fallback, no assignment decision is written; the request can still be created on a later retry.
6. an already-assigned run: no second decision, no review request.

**Server-only build-time boundary**. §33 documented the service-role module (`lib/semantic-topic/human-review-service.ts`) as a convention only ("no build-time enforcement of this in the repo today"). This gate closes that gap with `import 'server-only'` at the top of that file — the same mechanism Next.js applications conventionally use — but the official `server-only` npm package is not present anywhere in this repository's dependency graph, and installing one from the network was out of scope for this gate. Instead, `local-packages/server-only/` is a small, local, network-free reimplementation, wired in via `"server-only": "file:./local-packages/server-only"` in `package.json` (resolved with `npm install --offline`, producing a plain symlink in `node_modules/`):

- `local-packages/server-only/index.js` — `module.exports = {}` (a genuine no-op).
- `local-packages/server-only/error.js` — throws immediately on import.
- `local-packages/server-only/package.json` — `"main": "index.js"` (resolved by Node.js/vitest/server contexts — must never throw), `"browser": "error.js"` (resolved by browser-targeted bundlers — must throw).

Two empirical findings shaped this exact shape, both confirmed by direct build-time and Node.js-require probes (temporary files, since deleted) rather than assumed from the official package's behavior:

1. **Next.js's own `server-only` detection is keyed on the literal import-specifier string `"server-only"`, not a generic `package.json` `"browser"`-field convention.** A first attempt, named `server-only-guard` with the identical `main`/`browser` split, compiled cleanly into a client bundle with no error at all — zero protection. Renaming the package (directory, `package.json` `"name"`, and the `dependencies` key) to exactly `server-only` made the identical code trigger Next.js's own official error ("You're importing a component that needs 'server-only'...") on a client-component import, with no other change. The browser/main split is still kept because it is what makes the package correct under every *other* bundler and under plain Node.js — Next.js's own name-keyed check does not strictly require it, but nothing else in the toolchain can be assumed to also be name-keyed.
2. **`main` must be the no-op, never the throwing module.** An intermediate attempt set `"main": "error.js"` (same as `"browser"`) — this correctly failed the client build, but also broke plain Node.js usage (`node -e "require('server-only')"` threw outside any browser context), which would have broken every vitest test that imports `human-review-service.ts`, including the entire live-orchestration E2E suite. The final, verified-both-directions shape sets `"main": "index.js"` (no-op) and only `"browser": "error.js"` (throws).

Verified concretely: a `'use client'` component importing `createReviewRequest` from `human-review-service.ts` fails `next build` with Next.js's own server-only error text; `npx vitest run tests/human-review-app-integration.test.ts` (which depends on this exact module) is completely unaffected. The pre-existing source-scanning test from §33 remains as defense-in-depth but is no longer the only protection — a client-bundle import now fails the build itself.

**Full regression** (both provider/cost and the §33 API surface): with the flag off, `callAnthropicForExtraction` call counts are exactly unchanged across a completed extraction; creating a review request under the flag never calls the provider; a retry never triggers a new extraction or a new provider call; `ai_extraction_control` (the separate, pre-existing AI-quota kill switch) behavior is unchanged; collector behavior is unchanged (untouched subsystem). All 5 reviewer-route tests, the forged-identity tests, the admin-client-never-constructed test, the decision `Idempotency-Key` tests, the cron fail-closed tests, and the service-operation-not-on-a-public-route scan from §33 were rerun unchanged and remain green.

**Test evidence**: the full suite (`npx vitest run`, real local Docker Supabase stack, Anthropic mocked) was run **twice**, back to back, to prove deterministic fixture cleanup and DB-state restoration under this phase's added save/restore logic for the `ai_extraction_control` kill switch and the `ai_provider_daily_budgets` daily counters (both pre-existing, shared, cumulative local state — not reset blindly, but saved exactly and restored exactly). Both runs: `89 passed | 2 skipped` (91 test files), `1216 passed | 37 skipped` (1253 tests), 0 failed, ~875–879s each. `tsc --noEmit` and `next build` both clean.

**Still deferred to later, separately-gated phases** (unchanged from §33, now the concrete next step): a reviewer UI of any kind; turning `SEMANTIC_TOPIC_HUMAN_REVIEW_ENABLED` on anywhere but a local test process; registering the expire cron in `vercel.json`; any automatic call to `executeApprovedReview`; the real reviewer-provisioning/bootstrap security gate. Production remains completely inactive; no reviewer bootstrap has occurred at any point in this phase.

## 35. Human-Reviewed Candidate Workflow — Structured Orchestration Outcome Closure (`outcome_kind` / `reason_code`, no message-text branching)

**Status: local application code only**, same posture as §33/§34. This gate replaces every regex-/message-text-based branch that `create_topic_assignment_review_request` (078) and its two application-layer callers (`human-review-service.ts`, `human-review-extraction-hook.ts`) used, with a stable, DB-derived, machine-readable `outcome_kind` + `reason_code` contract. §34's "re-classify by matching the RPC's message text" design — while functionally correct — is now fully retired for this one RPC; every other 078 RPC wrapper (decision/cancel/revoke/execute/expire, all handled by the shared `mapReviewRpcError`) is unaffected and still uses its own established UPPER_SNAKE_CASE message-tag convention, since that part of the contract was explicitly out of scope for this gate.

**Function identity unchanged**: name, parameters (`p_extraction_run_id UUID, p_idempotency_key TEXT`), owner (`postgres`), `SECURITY DEFINER`, `search_path = public, pg_temp`, ACL (`postgres` + `service_role` `EXECUTE` only), and the `0.8500` confidence ceiling are all byte-identical to §32/§34. Only the function **body**'s success/failure communication shape changed.

### Database outcome contract (`create_topic_assignment_review_request`'s JSONB return, every branch)

| SQL branch | Returns | `outcome_kind` | `reason_code` |
|---|---|---|---|
| fresh insert succeeds | `RETURN` | `created` | `NULL` |
| idempotency-key replay (pre-insert or post-`unique_violation` re-fetch, digest matches) | `RETURN` | `replayed` | `NULL` |
| `status <> 'completed'` | `RETURN` | `ineligible` | `EXTRACTION_NOT_COMPLETED` |
| `structured_output` / `specificity` / `confidence` / `supporting_spans` malformed or `NULL` (new guard, see below) | `RETURN` | `ineligible` | `INVALID_STRUCTURED_OUTPUT` |
| `specificity <> 'specific'` | `RETURN` | `ineligible` | `NOT_SPECIFIC` |
| `confidence >= 0.8500` | `RETURN` | `ineligible` | `CONFIDENCE_NOT_REVIEW_ELIGIBLE` |
| `jsonb_array_length(supporting_spans) < 1` | `RETURN` | `ineligible` | `NO_SUPPORTING_SPANS` |
| an existing `topic_assignment_decisions` row already exists for this run | `RETURN` | `blocked` | `ALREADY_ASSIGNED` |
| `unique_violation` on `idx_topic_assignment_review_requests_one_live_per_run` (concurrency loser) | `RETURN` | `blocked` | `LIVE_REVIEW_REQUEST_EXISTS` |
| idempotency key reused for a different `extraction_run_id`, or same run with a genuinely different payload | `RAISE EXCEPTION` (unchanged) | — | — (message-tagged `IDEMPOTENCY_KEY_REUSE`, deliberately left as a raised, controlled conflict — see below) |
| `extraction_run_id` not found (pre- or post-advisory-lock) | `RAISE EXCEPTION` (unchanged) | — | — |

`UNSUPPORTED_EXTRACTION_VERSION` was **not** added: the actual RPC body has no `extraction_schema_version`/`normalization_version` gate anywhere in `create_topic_assignment_review_request`, and this gate's brief explicitly forbade inventing a check that isn't implemented.

**Why `IDEMPOTENCY_KEY_REUSE` and "not found" stay as `RAISE EXCEPTION`, unconverted**: both remain a controlled, non-leaking conflict/error (the raw `unique_violation`/message never reaches the caller — this was already true before this gate) but are not part of the closed `outcome_kind`/`reason_code` return contract. This is deliberate, not an oversight: the extraction hook's own fail-closed default (any thrown exception → `retryable_failure`, see below) already handles both correctly and safely without any dedicated mapping, and the real orchestration path (`maybeRequestHumanReview()`) derives its idempotency key deterministically from the extraction run's own id, so a genuine `IDEMPOTENCY_KEY_REUSE` from that call site is already an anomaly, not a normal outcome needing its own hook-level branch.

**`INVALID_STRUCTURED_OUTPUT` — a real, found-and-fixed correctness gap, not new business logic**: in PL/pgSQL, `IF NULL THEN ... END IF` evaluates the comparison to SQL `NULL`, which is treated as `false` — the branch is silently *skipped*, not entered. Before this gate, if `structured_output->>'specificity'` (or `confidence`, or `supporting_spans`) were ever SQL `NULL` on a `'completed'` row, the `specificity <> 'specific'` / `confidence >= ceiling` / `jsonb_array_length(...) < 1` checks would all silently evaluate to `NULL` and be skipped — letting a malformed extraction slip through as "eligible". Verified concretely: inserting a `'completed'` extraction run with `"specificity": null` via `record_topic_extraction_run` (074 does not reject a `null` specificity value; only the application-layer validator in `structured-output-schema.ts` does, and that layer is bypassed by direct-SQL fixtures) previously would have passed straight through the old code to a live review-request creation. The new guard (`structured_output IS NULL OR ...->>'specificity' IS NULL OR ...->>'confidence' IS NULL OR jsonb_typeof(...->'supporting_spans') IS DISTINCT FROM 'array'`) closes this precisely, before any of the three original checks run. This does not change what counts as eligible for any extraction actually produced by this codebase's real write path (which already guarantees non-null values) — it only converts a previously-silent, always-unintended bypass into an explicit, structured `ineligible` result.

### Application mapping (`lib/semantic-topic/human-review-service.ts`, `lib/semantic-topic/human-review-extraction-hook.ts`)

`createReviewRequest()`'s `CreateReviewRequestResult` is a discriminated union keyed on `outcome`: `'success'` (carries `outcomeKind: 'created' | 'replayed'`), `'blocked'` (carries `reasonCode: 'ALREADY_ASSIGNED' | 'LIVE_REVIEW_REQUEST_EXISTS'`), `'ineligible'` (carries `reasonCode` from the five-value ineligible set), `'database_error'`, `'invalid_rpc_response'`. It parses the RPC's JSONB body directly by field (`body.ok`, `body.outcome_kind`, `body.reason_code`), validated against closed `Set`s of the known reason codes — never a regex or `.includes()` against `body.message`. A thrown RPC exception (the two unconverted branches above, or any real connection/transport failure) is mapped uniformly to `database_error` without inspecting `error.message` at all — `mapReviewRpcError`'s shared, message-pattern-matching fallback (still used by every other 078 RPC wrapper) is deliberately **not** called from `createReviewRequest()` any more.

`maybeRequestHumanReview()` (`human-review-extraction-hook.ts`) then switches exhaustively on that typed result:

| `createReviewRequest()` result | `HumanReviewOrchestrationResult` |
|---|---|
| `{ outcome: 'success', outcomeKind: 'created' }` | `{ outcome: 'created', ... }` |
| `{ outcome: 'success', outcomeKind: 'replayed' }` | `{ outcome: 'replayed', ... }` |
| `{ outcome: 'blocked', reasonCode: 'LIVE_REVIEW_REQUEST_EXISTS' }` | `{ outcome: 'pending' }` |
| `{ outcome: 'blocked', reasonCode: 'ALREADY_ASSIGNED' }` | `{ outcome: 'already_assigned' }` |
| `{ outcome: 'ineligible', reasonCode: <any of the 5> }` | `{ outcome: 'not_eligible', message }` |
| `{ outcome: 'database_error' | 'invalid_rpc_response' }` | `{ outcome: 'retryable_failure', message }` |
| anything else (a future/mismatched shape TypeScript's exhaustive switch doesn't recognize) | `{ outcome: 'retryable_failure', ... }` — explicit fail-closed default, never reached if the union stays exhaustive, kept as a last-resort guard |

**Fail-closed rule, restated precisely**: an unrecognized or missing `outcome_kind`/`reason_code` pair can **never** resolve to `not_eligible`, `already_assigned`, or `pending` — only an explicitly recognized, closed-set value can. Every unrecognized shape resolves to `retryable_failure`, so the caller never mistakes "we don't understand this response" for "this run is settled" and never lets an unrecognized state silently continue into the old assignment/QUARANTINE path.

**`message` is diagnostic-only, by test, not just by convention**: a dedicated DB-integration test (`tests/semantic-topic-human-review-rpcs-db-integration.test.ts`, "changing the human-readable message text alone never changes outcome_kind/reason_code") and a unit test (`tests/human-review-extraction-hook.test.ts`, "not_eligible mapping is identical regardless of message content") both assert the same `outcome_kind`/`reason_code` pair with two completely different `message` strings.

**No regex/message branching — proven, not just claimed**: two static source-scan tests (`tests/human-review-extraction-hook.test.ts`) strip comment lines and assert no `.test(`, `.exec(`, or `message.includes(` call exists anywhere in `human-review-extraction-hook.ts`, and no `mapReviewRpcError(` call exists inside `createReviewRequest()`'s own function body.

**`tests/human-review-error-mapping.test.ts` regression, found and fixed by this gate's own full-suite run**: this pre-existing unit-test file asserted that `mapReviewRpcError` classified five `create_topic_assignment_review_request`-specific message strings as `not_eligible` — exactly the regex branch this gate removes. Since `createReviewRequest()` no longer calls `mapReviewRpcError` at all, and the RPC no longer raises those five messages (they are now structured `ineligible`/`blocked` returns), those five assertions were updated to expect the correct new behavior: an unrecognized message now falls through `mapReviewRpcError`'s generic `database_error` default. This was caught by the mandated full local `npx vitest run` — a concrete instance of why this rollout requires running the complete suite, not just the newly-written tests, before every commit.

### Concurrency and replay (real parallel connections, `tests/semantic-topic-human-review-rpcs-db-integration.test.ts`)

- Two concurrent creates on the same run, different keys: both processes now exit 0 (no exception); the loser's JSONB body is `{ ok: false, outcome_kind: 'blocked', reason_code: 'LIVE_REVIEW_REQUEST_EXISTS' }`, distinguished from the winner by the RPC's own `ok` field, never by process exit code.
- An already-assigned run: `{ ok: false, outcome_kind: 'blocked', reason_code: 'ALREADY_ASSIGNED' }`, structurally, in every code path that reaches it (up-front check, post-rejection, post-CREATE_NEW-execution, post-ATTACH_EXISTING-execution).
- Identical idempotency key + identical payload: replay, unchanged (`outcome_kind: 'replayed'`).
- Identical key + different payload/run: unchanged, controlled `IDEMPOTENCY_KEY_REUSE` exception, raw `unique_violation` never leaks.

### Migration safety (078)

The updated function body is applied via a **one-time, exact-hash-gated upgrade branch**, not a general drift handler: `create_topic_assignment_review_request`'s pre-existing VALIDATE path first checks whether the *currently installed* body hash equals the one known pre-release hash this exact function has ever had in any local/disposable dev DB (`e66bbbbc216ad678965c8c6906f7903a`) — if so, and only so, it performs a scoped `DROP FUNCTION public.create_topic_assignment_review_request(UUID, TEXT)` followed by the ordinary CREATE branch, landing on the new hash (`b2dc0bf3cde341c21efc5023dd32ac04`). Any other unrecognized existing body still hits the original fail-closed drift exception, unchanged. ## 37. Human-Reviewed Candidate Workflow — ATTACH_EXISTING/`duplicate_search_outcome` contract correction (migration 084)

**Status: local only, not deployed to production.** Migration 084 is additive-only: it widens one CHECK constraint's allowed value set, adds one new CHECK constraint, and `CREATE OR REPLACE`s `record_topic_assignment_review_decision` (078) with a corrected body (same signature, same digest formulas — see below). Nothing here touches 077's four tables' shape, 078's other seven RPCs, `record_topic_assignment_decision` (074), or `execute_approved_topic_assignment_review`'s own body (078) — all confirmed byte-identical by this migration's own final self-check, the same pattern 077/078 already established.

**The bug this migration fixes.** §31 introduced `duplicate_search_outcome` with exactly two allowed values — `no_duplicate_found` and `possible_duplicate_reviewed_and_distinct` — applied identically regardless of `proposed_outcome`. This was never correct for `ATTACH_EXISTING`: attaching to an existing topic means the reviewer *found* a matching identity, and both legacy values assert the opposite (`no_duplicate_found` denies a match outright; `possible_duplicate_reviewed_and_distinct` affirmatively asserts the candidate found is DISTINCT from the evidence at hand — the exact opposite of what attaching means). This was caught live: a real production review request (evidence prefix `62ce9381`, review request prefix `02f2a5ac`, target topic prefix `4db5d1c1`) is stuck `pending` because no available `duplicate_search_outcome` value could truthfully describe an `ATTACH_EXISTING` decision for it.

**The fix — one new closed enum value, `existing_topic_match_confirmed`** ("the reviewer verified the candidate semantic identity matches an already-existing topic, and the ATTACH_EXISTING target is correct"; Hungarian UI label `Egyező meglévő topic megerősítve`), plus a fail-closed pairing rule enforced identically at three layers (this codebase's established belt-and-suspenders style):

| `proposed_outcome` | allowed `duplicate_search_outcome` |
|---|---|
| `ATTACH_EXISTING` | `existing_topic_match_confirmed` only |
| `CREATE_NEW` | `no_duplicate_found` or `possible_duplicate_reviewed_and_distinct` only (`existing_topic_match_confirmed` forbidden) |
| *(not yet chosen — `pending`/`rejected`/`expired`/`cancelled`)* | n/a — both fields are `NULL` in these states, per 077's own existing per-status field-completeness CHECKs, unchanged |

1. **DB CHECK** — `topic_assignment_review_requests_dup_search_check` (077) widened from two to three allowed values; a new constraint, `topic_assignment_review_requests_dup_search_outcome_pairing`, encodes the pairing rule directly as a same-row, two-column CHECK, using the identical `proposed_outcome IS NULL OR (...)` idiom 077's own `..._create_new_no_target`/`..._attach_requires_target` CHECKs already use — so a not-yet-decided request (both columns `NULL`) always passes, and the rule only ever engages once `proposed_outcome` is actually filled in (`approved`/`revoked`/`executed`).
2. **RPC application-level validation** — `record_topic_assignment_review_decision`'s existing `IF ... RAISE EXCEPTION` validation ladder (the same function, same file-replacement pattern already used by 076 for `record_topic_extraction_run`/`reserve_ai_provider_units`) gained two new checks, placed immediately after the existing "approved requires the full structured review snapshot" `NULL` check (so `p_duplicate_search_outcome` is already proven non-`NULL` by the time they run): `ATTACH_EXISTING` + anything other than `existing_topic_match_confirmed` → `RAISE EXCEPTION ... ATTACH_EXISTING requires duplicate_search_outcome=existing_topic_match_confirmed`; `CREATE_NEW` + `existing_topic_match_confirmed` → `RAISE EXCEPTION ... CREATE_NEW requires duplicate_search_outcome no_duplicate_found or possible_duplicate_reviewed_and_distinct`. Every other line of the function — lock order, expiry check, replay/idempotency dispatch, `ATTACH_EXISTING` target-lifecycle re-validation, the `rejected` branch's atomic `QUARANTINE` insert — is untouched, byte-identical to 078's original body apart from these two new `IF` blocks.
3. **TypeScript** — `DuplicateSearchOutcome` (both `lib/semantic-topic/human-review-types.ts` and its deliberate client-side duplicate `components/semantic-topic-reviews/types.ts`, see §36's rationale for why that duplication exists) widened to the three-value union; a new `allowedProposedOutcomesForDuplicateSearchOutcome()` helper (in both files, independently) is a `switch` over `DuplicateSearchOutcome` with a `never`-exhaustiveness `default` branch — matching the same idiom `human-review-http-mapping.ts`'s status-mapping switch already uses — so a future 4th `duplicate_search_outcome` value fails the TypeScript build until this function is told which `proposed_outcome`(s) it is valid for. The admin API route (`app/api/admin/semantic-topic-reviews/[id]/decision/route.ts`) calls this helper before the RPC, returning 422 on a mismatched pairing; `decisionLogic.ts`'s `validateApprovalFields` calls the same helper for immediate client-side UX feedback. In every layer, the RPC/table CHECK remains the actual enforcement point — the TypeScript checks are fail-fast conveniences only, never a substitute.

**Reviewer UI** (`components/semantic-topic-reviews/DecisionForm.tsx`): the duplicate-search-outcome `<select>` now renders only the options valid for the currently-chosen `proposedOutcome` (`duplicateSearchOutcomesFor()` in `types.ts`; before a `proposedOutcome` is chosen, all three render, since that field is presented first in this form's existing layout). Switching `proposedOutcome` calls `decisionLogic.ts`'s new `resolveDuplicateSearchOutcomeOnProposedOutcomeChange()` — a pure, DOM-free function (same rationale as every other piece of this form's logic living outside the `.tsx` file — see §36 — this repo has no component-rendering test infrastructure) — which keeps the current selection if it is still valid, auto-selects `existing_topic_match_confirmed` when switching to `ATTACH_EXISTING` (its only valid option), or resets to unselected when switching to `CREATE_NEW` (two valid options — no guessing which one the reviewer meant). This is unit-tested directly (`tests/human-review-ui-decision-logic.test.ts`), not merely described.

**Digest formula — unchanged, `approval_digest_version` stays `1`.** Both `decision_operation_digest` and `approval_digest` embed `duplicate_search_outcome` via the same `to_json(p_duplicate_search_outcome)::text` call as every other field — a value-agnostic serialization. Migration 084 widens `duplicate_search_outcome`'s legal *value set*; it does not add, remove, reorder, or retype any field in either digest's canonical `format()` string. A digest-version bump exists in this codebase's convention to mark a change to the digest *formula* (field list/order/domain-separator — e.g. §30's `normalization_version` bump for a genuinely new canonicalization algorithm), not a change to one field's allowed values within an unchanged formula. `execute_approved_topic_assignment_review` (078, unmodified by 084) already recomputes `approval_digest` from the row's *current* stored fields and compares — since its own `to_json(...)` call is equally value-agnostic, it transparently accepts and correctly verifies a row carrying `existing_topic_match_confirmed` with no code change of its own, and this is proven by a dedicated test (`tests/semantic-topic-human-review-rpcs-db-integration.test.ts`, "ATTACH_EXISTING + existing_topic_match_confirmed + valid target" through to execution, reusing the same `corroborating`-transition assertions already established for the pre-084 `ATTACH_EXISTING` path). There is no Node-side (TypeScript) computation of `approval_digest`/`decision_operation_digest` anywhere in this codebase to keep in parity — both digests are computed exclusively inside this one SQL function — so the Node/SQL parity-test pattern used elsewhere for `decisions_digest_v2` (`tests/decisions-digest-db-integration.test.ts`, an unrelated digest over `topic_assignment_decisions` rows) does not apply here; the correctness proof for this digest is instead the RPC's own recompute-and-compare replay logic, exercised end-to-end by the tests above.

**Historical-compatibility risk: none.** A CHECK constraint only ever applies to rows written *after* it is added (Postgres validates existing rows once, at `ADD CONSTRAINT` time, against the constraint being added — not retroactively on every future read) — 077/078's own established pattern (see §30's "the v1 production row is immutable" and §31's "no retroactive re-validation of old rows" precedent) already relies on this. Every pre-084 row (including every existing `CREATE_NEW` decision made with the legacy two-value set, and the stuck `02f2a5ac…` `ATTACH_EXISTING` request itself) satisfied the *old*, narrower dup-search CHECK, which is a strict subset of the new one — so 084's `ADD CONSTRAINT` validation pass over existing rows cannot fail for any legacy `CREATE_NEW` row, and it does not touch (`UPDATE`) any existing row at all. A historical row continues to read, and — if not yet decided/executed — replay, exactly as before; proven directly (`tests/semantic-topic-human-review-rpcs-db-integration.test.ts`, "a historical CREATE_NEW decision made before 084 still replays correctly after 084"). The one stuck production row remains stuck after this local migration is written — production is out of scope for this gate entirely (no remote DB access) — but it becomes correctly decidable (`ATTACH_EXISTING` + `existing_topic_match_confirmed`) the moment this migration is separately, explicitly rolled out to production, which is **not** part of this local gate.

## 38. Eligible source-identity correctness — `signal_source_id` as the canonical cross-evidence-type identity (migration 086)

**Status: local only, not deployed to production.** Migration 086 is additive-only: one new, `public`-schema-but-zero-external-grant helper function (`public._semantic_topic_eligible_membership_sources`), and `CREATE OR REPLACE` on three already-live functions (`record_topic_assignment_decision` — 074; `execute_approved_topic_assignment_review` — 078; `compute_topic_evidence_vector` — 085), each hash-gated against its known legacy body exactly as 084 established for `record_topic_assignment_review_decision`. The historical 072/074/078/084/085 migration *files* are unmodified.

**The bug this migration fixes.** The `candidate_singleton → corroborating` automatic transition (the only automatic lifecycle transition this codebase makes) compared a raw `count(*)` of active `semantic_topic_membership` rows against 2 — not a count of *distinct known sources*. Three concrete false-positive paths followed from this: two memberships from the *same* YouTube channel would wrongly trigger `corroborating` (mechanically "2 memberships" but only 1 real source); two memberships with an unresolvable source would trigger it with zero known sources; and a membership whose evidence is a known syndication copy of another already-counted evidence would double-count one piece of content as two independent confirmations. Separately, `compute_topic_evidence_vector` (085) computed its own, differently-scoped `knownIndependentSourceCount` by joining `youtube_videos.channel_id` — a **nullable, `ON DELETE SET NULL`** convenience FK that only exists for YouTube evidence — instead of `signal_evidence.signal_source_id`, the actual **`NOT NULL`, `ON DELETE RESTRICT`** canonical source reference that already exists, uniformly, for every evidence type (`signal_sources.source_type IN ('youtube_channel', 'web_domain')`, populated at capture time by `lib/emerging-signal/capture.ts`'s `deriveYoutubeSourceKey`/`deriveWebSourceKey`). The transition-trigger logic and the reporting RPC could therefore silently disagree with each other, and the reporting RPC's own source-resolution path was structurally fragile (a future `youtube_videos` row cleanup could spuriously flip a topic's reported source count without any change to the actual evidence).

**"corroborating" is a mechanical claim, not a proof of independence.** `eligibleDistinctSourceIdentityCount` (see below) proves only: distinct, known `signal_source_id` values, among active memberships whose evidence is not a known syndication copy. It does **not** prove editorial/authorial independence (a distinct channel can still be a derivative, a reupload, or content from the same production outfit) and it does **not** prove semantic identity coherence (that the evidence genuinely describes the same real-world phenomenon). Both of those are exclusively a `coherent`-transition human-review responsibility (a separate, not-yet-implemented phase) — `corroborating` and its automatic trigger only ever assert **mechanical source diversity**.

**The fix — one shared helper, `LANGUAGE sql STABLE`, plain (not `SECURITY DEFINER`), zero external grants:**

```
public._semantic_topic_eligible_membership_sources(p_semantic_topic_id UUID)
  RETURNS TABLE (
    membership_id UUID, evidence_id UUID, source_identity_id UUID, source_type TEXT,
    assignment_reason TEXT, algorithm_version INTEGER, confidence NUMERIC,
    evidence_type TEXT, evidence_identity_complete BOOLEAN
  )
```

`source_identity_id` is simply `signal_evidence.signal_source_id` (via a `LEFT JOIN signal_sources` — `LEFT`, not `INNER`, purely to keep `eligibleMembershipCount` counting *every* eligible membership regardless of source resolution, not because a `NULL` is reachable today: the column is `NOT NULL` with `ON DELETE RESTRICT`, so under the current schema `source_identity_id` is always non-`NULL` for every row the helper returns). `COUNT(DISTINCT source_identity_id)` is therefore the single, shared, correct definition of "how many mechanically distinct known sources" — used identically by the `candidate_singleton → corroborating` trigger in both 074 and 078 (`SELECT count(DISTINCT source_identity_id) FROM public._semantic_topic_eligible_membership_sources(...) >= 2`) and by `compute_topic_evidence_vector`'s `eligibleDistinctSourceIdentityCount` field. `algorithm_version`/`confidence` are carried on the helper's output (beyond the minimum columns) solely so 085's `byAlgorithmVersion`/`confidenceDiagnostics` diagnostics can be derived from this one shared row-set too, rather than duplicating a second, parallel eligibility query inside 085's own body.

**Security topology.** The helper has **no** `EXECUTE` grant to `PUBLIC`, `anon`, `authenticated`, or `service_role` — reachable only from inside the three `postgres`-owned `SECURITY DEFINER` callers above (a `SECURITY DEFINER` function's un-decorated callees run under the definer's own privileges, so the owner needs no separate grant to call its own helper). Postgres grants `EXECUTE` to `PUBLIC` by default on every new function; this migration explicitly `REVOKE`s it (defense in depth, not an assumption). `has_function_privilege()` cannot take the `'PUBLIC'` pseudo-role as an argument (it is a `GRANT`/`REVOKE` keyword, not a row in `pg_roles`) — the self-check instead uses `aclexplode()` directly, excluding the function owner's own implicit `ALL PRIVILEGES` ACL entry (which Postgres materializes automatically the first time any `REVOKE` is issued against a function that previously had only the implicit default ACL).

**`inputIntegrityStatus` — now evidence-type-aware, and derived from exactly two named booleans, never a fourth ad-hoc branch:**

- **`evidenceIdentityComplete`** — `true` only if every eligible membership's evidence satisfies its own type's stable-identity condition: `youtube_video` → non-blank `external_ref` (the `signal_evidence_identity_key` UNIQUE/NOT NULL column — effectively always true for any row that exists at all); `serper_web`/`serper_news` → non-blank `canonical_url` (already enforced NOT NULL for non-YouTube rows by the 051 `signal_evidence_canonical_url_required` CHECK). Any future, not-yet-supported `evidence_type` value is treated as incomplete — fail-closed, never assumed safe.
- **`sourceIdentityKnown`** — `true` only if every eligible membership's `signal_source_id` resolves to a `signal_sources` row. Structurally always true today (see above); kept as an explicit, independently-computed field rather than hardcoded, since it is the correctness-relevant question a future schema relaxation would need to answer.
- **Vacuous-case rule** — an empty eligible set does **not** silently read as `true` for either boolean (SQL's `bool_and()` over zero rows is `NULL`, which this migration explicitly `coalesce`s to `false`) — "nothing to evaluate" is fail-closed `false`, never a misleading claim of completeness.
- **`inputIntegrityStatus`** — `'not_applicable'` if `eligibleMembershipCount = 0`; `'complete'` iff both booleans are `true`; `'incomplete'` otherwise. No other condition feeds this field.

The previous, YouTube-only-`canonical_url`-based definition produced a false `'incomplete'` for entirely valid YouTube evidence (`canonical_url` is deliberately `NULL` there by schema design — see §"YOUTUBE EVIDENCE FK/CHECK JAVITAS" in `051_signal_evidence.sql`'s own header). The corrected definition uses each type's actual stable identifier instead.

**JSON contract: `knownIndependentSourceCount` removed, `eligibleDistinctSourceIdentityCount` is now canonical.** A source-code audit found zero consumers of the old field name anywhere outside 085's own migration file and its own test file (`compute_topic_evidence_vector` has never had an `authenticated` grant, and no `lib/`/`app/` code calls it) — so this migration performs a clean rename, not a deprecated alias. `unknownSourceCount` (a membership whose `source_identity_id` did not resolve) is kept, unchanged in shape, as a defensive diagnostic for a case the current schema cannot actually produce.

**`serper_news` — CHECK-permitted, still writer-less.** The `signal_evidence_type_check` CHECK (051) has always allowed `'serper_news'` as a third `evidence_type`, but no capture code path has ever written one — `lib/emerging-signal/capture.ts`'s own header comment documents that the Serper News/Web distinction is lost upstream of this codebase's boundary, so every web result is recorded as `'serper_web'`. This migration's helper and `compute_topic_evidence_vector` both handle `'serper_news'` correctly (same `canonical_url`-based identity rule as `'serper_web'`, same `web_domain` source-type family) and this is proven with a real, synthetic `'serper_news'` DB fixture (not merely a documentation note) — but production has zero rows of this type today, and no code path creates one.

**Web-domain normalization — `www.`-only, already live, not invented here.** `lib/emerging-signal/normalize.ts`'s `extractDomain()` (used by `deriveWebSourceKey()` at capture time to populate `signal_sources.external_id` for `source_type='web_domain'`) strips only a leading `www.` prefix (`hostname.toLowerCase().replace(/^www\./, '')`) — it does **not** collapse other subdomains to a shared parent-domain identity (e.g. `news.example.com` and `example.com` remain two distinct `signal_sources` rows). This is the schema's actual, already-shipped behavior, reused as-is by this migration's helper — not a new limitation introduced here, and not something this migration attempts to fix (a public-suffix/eTLD+1-aware normalization would be a separate, deliberately-calibrated future decision, not a default to reach for without real web-evidence production data to calibrate against — production currently has zero `serper_web`/`serper_news` rows).

**Stored lifecycle + live evidence-vector — the intended dual-gate shape for any future consumer.** `lifecycle_status` is a stored column and does **not** automatically demote when the evidence backing a `corroborating`/`coherent` topic later shrinks (a membership's `valid_to` is set, its evidence is marked a syndication copy, etc.) — no code path in this phase writes such a demotion, and none should be added without a separately-designed, explicitly-authorized gate (automatic backward transitions were already rejected on fail-closed grounds in the Lifecycle v1 design gates). Any future production consumer (Creator Lane or another user-facing surface) must therefore treat topic eligibility as a **two-part, always-live** check, never the stored status alone: (1) `lifecycle_status` is in an explicit allowlist (`{'corroborating', 'coherent'}`), **and** (2) a fresh `compute_topic_evidence_vector()` call, made at or near consumption time, still meets the same minimum (`eligibleDistinctSourceIdentityCount >= 2` for `corroborating`) and integrity conditions. This is a design note for that future consumer, not something implemented in this migration.

**Backlog note — lifecycle-review expiry transaction shape (not part of this migration).** A future lifecycle-review executor RPC must not both persist an `expired` state transition and `RAISE EXCEPTION` in the same call — an uncaught exception rolls back everything in the current transaction, including that same `UPDATE`. The correct shape (already the pattern `compute_topic_evidence_vector`'s own `TOPIC_NOT_FOUND` branch uses): persist the state change, then `RETURN` a normal, non-exception `{ok: false, reasonCode: 'REQUEST_EXPIRED'}` JSONB — `RAISE EXCEPTION` stays reserved for branches with no state to persist.

**DB-integration tests** (`tests/semantic-topic-eligible-source-identity-086-db-integration.test.ts`): helper correctness (same-channel/different-channel/syndication-copy/inactive-membership/cross-type-non-collision), helper security boundary (`anon`/`authenticated`/`service_role` all rejected on direct call; `service_role` succeeds through `compute_topic_evidence_vector`), 074 and 078 corroborating-enforcement regression (including the real production shape — two distinct known YouTube channels), the new `compute_topic_evidence_vector` JSON contract (vacuous-case fail-closed booleans, evidence-type-aware integrity, cross-type non-inflation, `serper_web`/`serper_news` correctness), static source-guard proofs (no raw `count(*)` lifecycle trigger remains; all three consumers reference the one shared helper by name), and migration idempotency (clean no-op reapply; an unrecognized body hash fails closed with no DDL and is cleanly restorable to the audited corrected body).

**Migration mechanics** (`supabase/migrations/084_semantic_topic_attach_duplicate_outcome_contract.sql`): follows the exact fail-fast CREATE-or-VALIDATE convention every migration in this repo uses — a preflight gate confirms the 077/078 baseline objects exist; the CHECK-widening step reuses 077's own §5-block idiom exactly (compare `pg_get_constraintdef()` against known legacy/corrected text constants, `DROP`+`ADD` only from the known legacy text, `RAISE EXCEPTION DEFINITION_DRIFT` on anything else); the new pairing CHECK is existence-gated (`ADD` if absent, byte-exact-text `VALIDATE` if present, `RAISE EXCEPTION` on any other text); the RPC replacement reuses 076's own function-hash-gate idiom exactly (pre-replace signature/owner/`SECURITY DEFINER`/`search_path`/ACL audit, hash-gated `CREATE OR REPLACE` from a pinned legacy body hash only, post-replace re-audit of everything including the ACL, which `CREATE OR REPLACE FUNCTION` preserves automatically when the signature is unchanged). A final self-check block (mirroring 077 §6 exactly) re-confirms `record_topic_assignment_decision` (074) and `execute_approved_topic_assignment_review` (078) are untouched. No `CASCADE` anywhere; one transaction (`BEGIN...COMMIT`). Applying the migration twice against the same local Postgres instance was verified directly (not merely reasoned about) to be a byte-exact no-op — every branch reports `-- no-op` on the second run, and the function/constraint hashes are identical before and after. An injected, unrecognized prestate (a hand-edited pairing-CHECK definition matching neither the known legacy nor corrected text) was also verified directly to fail closed — `RAISE EXCEPTION`, full transaction rollback, zero DDL applied — before being reverted and the migration re-run to confirm it restores the correct state.

## 39. Lifecycle Review Framework v1 — the four v1 transitions, request/decision/executor authority split (migration 087)

**Status: local only, not deployed to production.** Migration 087 is additive-only: three new tables (`semantic_topic_lifecycle_review_requests`, `semantic_topic_lifecycle_review_events`, `semantic_topic_lifecycle_transition_events`) and four new `SECURITY DEFINER` RPCs. It never touches `compute_topic_evidence_vector` or the 086 eligible-source helper — the final self-check re-confirms their body hash is exactly `73aeb37846bcc80fd42a4e2c8862dc7c`/`fba8af744970df7f93ba96fd71d2a939` and aborts otherwise.

**Exactly four supported transitions in v1**, enforced simultaneously at three independent layers (RPC application logic, a table `CHECK` constraint, and the `create_*` RPC's own from/target validation) so no combination can silently slip through any one layer alone: `corroborating → coherent`, `corroborating → ambiguous`, `ambiguous → corroborating`, `ambiguous → coherent`. Every other `(from_status, target_status)` pair — including `split_required`, `merge_candidate`, `superseded`, `archived`, `candidate_singleton` as either side — is rejected with `UNSUPPORTED_TRANSITION`. This migration deliberately adds **no writer** for those five states; they remain documented-only `CHECK` enum members, exactly as the Lifecycle v1 design gates concluded. There is no automatic lifecycle demotion anywhere in this framework.

**Mechanical corroboration vs. human-confirmed coherence — restated, now enforced in code, not just prose.** `eligibleDistinctSourceIdentityCount >= 2` (086) is checked at `coherent`-target request-creation time and again, freshly, at execution time — but it is a **floor precondition**, never a sufficient one. The actual `corroborating → coherent` / `ambiguous → coherent` transition can only ever be recorded by `record_semantic_topic_lifecycle_review_decision`, which requires all four of `same_semantic_identity_confirmed`, `no_material_identity_conflict`, `canonical_definition_scope_fit_confirmed`, `provenance_relationship_reviewed` to be explicitly `TRUE` — a `CHECK` constraint (`sltrr_coherent_checklist_required`) independently re-enforces this at the table level for any `approved`/`executed` row. A `reviewer_rationale` string is required but is documented, and enforced, as insufficient on its own — the four booleans cannot be satisfied by rationale text.

**Three-tier authority boundary**, mirroring 077/078's own already-proven separation: `create_semantic_topic_lifecycle_review_request` is `service_role`-only (a client supplies only `semantic_topic_id`, `target_status`, and an idempotency key — never a snapshot, digest, `from_status`, `expected_status_version`, or `generation`, all of which are computed server-side under a topic-scoped advisory lock); `record_semantic_topic_lifecycle_review_decision` and `cancel_semantic_topic_lifecycle_review_request` are `authenticated`-only and derive the actor exclusively from `auth.uid()` plus a `semantic_topic_reviewers ... FOR SHARE` active-membership check — neither accepts a `p_reviewer_id`/`p_actor_id` parameter; `execute_approved_semantic_topic_lifecycle_transition` is `service_role`-only and accepts only `review_request_id` + an execution idempotency key, never an actor — it executes the decision already recorded (and `auth.uid()`-attributed) in step two.

**Snapshot canonicalization and staleness.** `evidence_vector_snapshot` is the raw `compute_topic_evidence_vector()` JSONB, captured once at request-creation time; its digest is `sha256` over a fixed-field `format()` string embedding `snapshot::text` — `jsonb::text` is Postgres's own deterministic canonical form for a given logical document (key order is never insertion-order-preserving), so the digest is provably independent of JSON key order or session formatting without any bespoke canonicalization step. At execution time the RPC recomputes `compute_topic_evidence_vector()` fresh and recompares the digest; any difference (a new membership, a membership closing, any contractual vector field changing) returns a closed `{ok:false, reasonCode:'STALE_REVIEW_REQUEST'}` — never an automatic retry, never a silently-refreshed snapshot. `expected_status_version`, captured at request-creation time under the same topic lock, is independently re-checked against the topic's live `status_version` at execution time (`STALE_TOPIC_VERSION` on mismatch), and the topic's live `lifecycle_status` is re-checked against the request's stored `from_status` (`STALE_TOPIC_STATE`) — three independent staleness dimensions, checked separately, none inferred from the others.

**Idempotency, domain-separated per phase.** `willviral.semantic-topic.lifecycle-review-request:v1` / `...-decision:v1` / `...-cancel:v1` / `...-execution:v1` / `...-transition-event:v1` are five disjoint digest domains, each embedding the relevant immutable fields plus the phase's own idempotency key. Every RPC checks its own phase's replay/conflict dispatch **before** any status or expiry gate — an exact key+payload retry always returns the original result, regardless of what has happened to the request since (proven directly for create, decision, and execute in the DB-integration suite). Lock order is fixed and global: `create_*` takes a topic-scoped advisory lock only; `record_*_decision` and `cancel_*` take a request-scoped advisory lock and `FOR UPDATE` the request row only (never the topic); `execute_approved_*` takes the same request-scoped advisory lock, `FOR UPDATE`s the request row, and only then `FOR UPDATE`s the topic row — request-before-topic is the one ordering used anywhere both are locked, so no two RPCs in this framework can deadlock against each other.

**Expiry — corrected transaction shape, not the earlier flawed draft.** A `requested` request whose `expires_at` has passed is handled by `record_semantic_topic_lifecycle_review_decision` (the first RPC to touch it after expiry) via a persisted `UPDATE ... SET status='expired'` followed by a normal `RETURN {ok:false, reasonCode:'REQUEST_EXPIRED'}` — never `RAISE EXCEPTION` after the `UPDATE`, since an uncaught exception would roll back that same `UPDATE`. This directly resolves the backlog note recorded in §38.

**Stored lifecycle + live vector — unchanged double-gate design, now with a concrete producer of stored transitions.** This framework is the first code to actually move `lifecycle_status` beyond `corroborating`/`ambiguous`/`corroborating`; §38's dual-gate note for any future consumer (allowlist on stored status **and** a fresh live vector check) remains the required consumption pattern — this migration does not add a consumer, only the mechanism that changes the stored value.

**DB-integration tests** (`tests/semantic-topic-lifecycle-review-087-db-integration.test.ts`, 34 tests): all four transitions' full request→decision→execute path; every unsupported `(from_status, target_status)` combination rejected (including a CHECK-constraint-level rejection for a `target_status` outside the closed set); the coherent mechanical floor and all-four-checklist-fields enforcement (including a rationale-only attempt correctly rejected); ambiguous/corroborating-from-ambiguous reason-code enforcement from their own closed sets; approval alone never transitions the topic; the executor transitions `status_version` by exactly 1 and replays cleanly without a second transition-event row; stale-snapshot and stale-status_version both independently proven to fail closed; expiry persists cleanly with a normal (non-exception) return; idempotent replay and same-key/different-payload conflict for both `create` and `execute`; exactly one `requested` request per topic; `generation` increments across successive requests; the full permission boundary (`anon`/`authenticated`/`service_role` each rejected from the RPCs they must not call, including a non-reviewer authenticated user); `cancel` works on a `requested` request and correctly refuses an already-`approved` one; migration reapply no-op and unrecognized-hash fail-closed-with-restoration; and a static-source proof that no raw `active membership count(*)`-style mechanical lifecycle trigger exists anywhere in this framework — every transition in v1 is human-review-gated by construction, never automatic.
